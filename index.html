The knowledge layer for AI assistants and agents.

An AI assistant or agent is only as good as what it knows. cob-rag-engine gives every business you serve its own private knowledge base, with its own keys and model, measured search and a usage count to bill from. Put it on a website, call it from your app, or plug it into any AI agent over MCP and script it from the shell. You own the server, the data and the margin.

The engine does
  • Counts every answered question from the widget and the query API, per day, per client, per widget.
  • Adds tokens and an estimated model cost (prompt_tokens, completion_tokens, cost_usd).
  • Never loses or blocks a count. One atomic database upsert per answer; if metering hiccups, the visitor still gets the answer.
  • Scopes the report to the key: a client key sees itself, a tenant key its own clients, the admin key everyone. Up to a year per request.
You do
  • Set the price: per answer, per month, or a plan with a cap.
  • Pull the numbers into Razorpay, Stripe or a spreadsheet, from the API or the dashboard.
  • Invoice and collect. There is no payments code in the engine, on purpose.

Not counted: answers served from the query cache and retrieval-only calls (/query/retrieve). Widget, streaming and streamed-conversation token counts are estimated with the tokenizer; /query uses the model's own counts.

Inside the engine

From a messy PDF to searchable knowledge

Upload a file and the API replies straight away with a job number. A background worker does the slow part: it reads the file, splits it along its own headings and files it in three stores. Every box below is a real step in the code, in the order it runs.

terminal · your app
# 1. upload: the API replies straight away
$ curl $API/api/v1/ingest \
    -H "X-API-Key: ck_…" \
    -F file=@returns-policy.pdf
HTTP/1.1 202 Accepted
{"job_id": "3f9c…", "status": "queued"}

# 2. poll the job while the worker runs
$ curl $API/api/v1/ingest/jobs/3f9c… \
    -H "X-API-Key: ck_…"
{"status": "completed",
 "processed_documents": 1,
 "errors": null,
 "finished_at": "2026-09-29T10:42:07Z"}

Tap a stage to see what GET /api/v1/ingest/jobs/{id} reports at that point. A failure stops the job as failed and records the step it stopped at; network errors are retried up to 3 times.

How it splits a document

Most engines chop text every N characters, so a chunk can start mid-sentence and forget which section it came from. This one cuts where the author did: at headings. Each chunk carries its heading path, tables stay whole, and long sections get a little overlap.

  1. Split at headings. Every section keeps its path, like Returns policy > Refunds.
  2. Tables and code stand alone. A table becomes one chunk, stored as text plus a JSON copy.
  3. Right-size. Aim for about 300 tokens: tiny pieces merge (under 50), long ones split (over 1,000).
  4. Overlap. 64 tokens carry over between parts of the same section, never across sections or tables.
  5. Parent and child. A section cut into parts also gets one parent chunk holding the whole section.
what the embedding model reads · chunk 2
Returns policy > Refunds

Refunds go to the original card…

The heading path is added only to the text that gets turned into vectors (RAG_INDEX_HEADING_CONTEXT, on by default). The text you store, show and cite stays the plain chunk.

Exact duplicates

Same file twice? Skipped.

The SHA-256 fingerprint of the bytes is checked first. An identical file already in the corpus finishes at once with "Duplicate file, already ingested", and nothing is re-embedded.

Near-duplicates

Looks familiar? You decide.

In auto mode the first chunks are compared with what is already stored. A close match parks the job as pending_review until you call POST /api/v1/ingest/{job_id}/confirm; unconfirmed reviews expire after 7 days.

Versions and re-syncs

Updates, not copies.

Upload a file with a name the corpus already has and it stacks as a new version. Records re-sync by fingerprint: unchanged ones are skipped, and a changed record's old vectors go only after the new ones are in.

Clients and keys

Every client in its own room. One server for all of them.

Each business you serve gets its own knowledge base: its own search index, API key, model, prompt and encrypted LLM key. A key only opens the rooms under it. We ran 412 attacks in tests, from one client against another and against the account system, with keys and with dashboard sign-ins, and all 412 were refused.

01

Who holds which key

Four kinds of key, one per level. You keep the admin key. Tenants (tk_) group knowledge bases (ck_), and each knowledge base can have public widget keys (pk_) for its websites.

Secret keys travel as X-API-Key, widget keys as X-Widget-Key. Secret keys are shown once, when created or rotated. Client LLM keys: Fernet-encrypted, shown as ***, rotatable.

Deleting a knowledge base takes everything in it along: documents, chunks, jobs, conversations, usage rows and widget keys go in one database delete, then its search collection and stored files are dropped. Deleting a tenant only switches it off; its widgets stop answering.

Bring your own key

Your server. Anyone's model key.

You never have to pay for a single model call. Each client can save their own key, a client's app can send one with every request, and your key only fills the gaps. Every AI call follows the same order.

Uses this order
  • Writing the answer, with any model the client picked
  • Understanding the question: rephrasing and splitting, on the fast model
  • The three confidence judges
  • The AI re-ranker; with no key at all it falls back to the free local one
  • The Content Portal's AI clean-up (client's key, then yours)
Different rules
  • Embeddings: each client can have its own embedding model and encrypted key, set on the knowledge base, never per request, because questions must match the stored vectors.
  • The website widget never accepts a key from the browser; it uses the client's saved key or yours.
  • Keys are never shown back once saved, and can be rotated.

Three ways to charge for it

Choose per client, and change it any time by saving or clearing their key.

Zero model cost

The client pays their AI provider

Their key goes on their knowledge base. You charge for hosting, setup and support; the model bill never reaches you.

Resell

You pay, and mark it up

Leave their key empty and yours is used. The usage API counts requests, tokens and estimated cost per client, so you can bill with a margin.

Mix

A different deal per client

Big clients bring their own key, small ones run on yours, and a privacy-first client gets a local model through Ollama so nothing leaves your server.

Limits, honestly: keys are set per knowledge base, not per tenant, so a tenant with five knowledge bases saves its key five times. The speech-to-text key is engine-wide.

Head to head

RAGFlow is a document platform. This is a reseller engine.

RAGFlow is the most capable open-source RAG project and the fairest comparison. It is built for one company understanding its own messy documents. cob-rag-engine is built for one operator serving many companies. Pick by the job.

Where RAGFlow is ahead

  • Document understanding. DeepDoc OCR, layout and table recognition, 12 chunking templates (laws, papers, manuals, Q&A), plus MinerU, Docling and vision-model parsers.
  • Connectors. About 40, with incremental sync: Google Drive, Notion, Confluence, SharePoint, Slack, Jira, Salesforce, databases.
  • No-code building. A visual agent canvas, an ingestion pipeline builder, "knowledge compilation" into wikis, graphs and timelines, MCP server and client.
  • Reach. 91.5k stars, 454 contributors, a release every one to three weeks, 77 model providers, 7 chat channels, a hosted cloud from $29/mo.

Where cob-rag-engine is ahead

  • Built for serving clients. Tenant → knowledge base → key, a key per knowledge base, each client's own model and prompt. In RAGFlow a knowledge base belongs to a user account and API keys are account-wide[16].
  • A widget you can put on a stranger's website. Publishable key, domain lock, per-visitor and daily limits. RAGFlow's embed is an iframe that its maintainers acknowledge exposes the URL and key[17].
  • Billing data. Per-client, per-widget daily usage through an API. RAGFlow has no per-customer metering in open source.
  • Light. About 2 GB of RAM on CPU with Postgres, Qdrant and Redis, versus 16 GB and six backing services (Elasticsearch, MySQL, MinIO, NATS, Kvrocks, ClickHouse) on x86 only.
  • Measured. A public, re-runnable retrieval benchmark and a cross-client isolation test suite.

!Worth knowing before you put either one on the internet

RAGFlow's GitHub lists critical advisories including remote code execution (CVE-2026-45312, CVE-2026-28797, CVE-2026-24770) and a 9.8-severity token prediction flaw, and The Hacker News reported in September 2026 that attackers were exploiting exposed RAGFlow servers to steal LLM API keys[18][19]. Version 1.0 (released 29 September 2026) is a rewrite in Go with a one-way database migration[20]. cob-rag-engine is younger and has had far less outside scrutiny; that cuts both ways, so read SECURITY.md.

Indie vs funded

Funding buys features. It also sets priorities.

A venture-backed open-source project has to become a business, and the business is usually its own cloud or enterprise edition. That is not a criticism; it explains the licenses and the paywalls in the table above. Here is the honest trade.

What a funded project gives you, and costs you

  • Gives: a team, dozens of integrations, a visual builder, fast releases, a large community to ask.
  • Costs: license clauses aimed at competitors. Dify and FastGPT bar multi-tenant resale; Open WebUI bars rebranding above 50 users.
  • Costs: the features a reseller needs sit in the paid edition. Dify's multi-workspace, Onyx's white-label and analytics.
  • Costs: the roadmap follows investors. Flowise was acquired by Workday and archived in August 2026[21]; Verba and Cognita were archived; R2R has not released since June 2025; Quivr's company pivoted to a Zendesk tool.

What this independent project gives you, and costs you

  • Gives: the whole product in the repository. There is no ee/ folder and nothing held back for a paid tier.
  • Gives: a license that says yes to reselling. AGPL-3.0 lets you charge clients; a commercial license exists if you need to keep engine changes private.
  • Gives: one job, done carefully: multi-client RAG with a widget and billing data. Standard parts (Postgres, Qdrant, Redis, FastAPI) you can operate yourself.
  • Costs: one maintainer, fewer integrations, a small community. If you need a Notion connector tomorrow, you may be the one writing it. Every external dependency sits behind a swappable interface to make that practical.

What's in the box

Everything between a document and an answer

Everything a client-facing assistant needs, in one repository, with nothing held back for a paid edition.

Clients and keys

Admin, tenant, knowledge-base and publishable widget keys; secret keys are stored only as hashes. Each client's LLM key encrypted and rotatable. One search collection per client.

Website widget

One script tag, isolated from the host page's styles, streaming answers with sources, brand colour and position, mobile-ready. Domain allow-list and rate limits.

Ingestion

PDF (scanned too), Word, Excel, CSV, PowerPoint, HTML, Markdown, audio via Whisper, a website crawler, and a records API for catalogues. Duplicate detection and version history.

Search

Meaning-based and keyword search combined, tuned on public benchmarks. Optional re-ranking, diversity, recency boost and filters by metadata.

Answers

Citations to the exact section, a validation step that scores confidence, streaming, multi-turn conversations and memory. Any model through LiteLLM, or local models through Ollama. Reply language set per client: Hindi, Marathi and more.

Accounts built in

People sign up with an e-mail address and confirm it with a 6-digit code. You choose open sign-up, approval of each one, or closed. Passwords are hashed with argon2id; sign-ins use short-lived tokens that rotate.

Teams and plans

Each client gets a team with owner and member roles, invited by e-mail. Plans cap four things: knowledge bases, questions a month, documents and widget keys. Nothing is capped until you set a plan.

Your brand, your mail

Your product name, logo and colour on the sign-in pages, the dashboard and every e-mail, with a permanent small “cob-rag-engine by Callobuzz” line. E-mail goes out over your own SMTP server.

Operations

A dashboard for you and for each client's team, usage API, Python and JavaScript SDKs, tracing with Langfuse, answer evaluation, knowledge-gap reports, zero-downtime embedding model switches.

The short version

Should you build on it?

Three honest answers, depending on what you are building and who it is for.

Build on it

You want to sell AI assistants to other businesses

An agency, a niche chatbot SaaS, private deployments, or AI answers inside your own product. That combination (separate clients, a domain-locked widget, per-client usage, any model, a license that allows it, on a small server) is what the open-source field does not offer in one piece today.

Pick RAGFlow or Onyx

You are one company with heavy document needs

You need dozens of connectors, a no-code agent builder, or the deepest parsing of scanned documents, and you have the 16–24 GB server to run it.

Pick a hosted tool

You need one chatbot, this afternoon

One chatbot for one website, and you never want to run a server: a hosted tool like Chatbase is the faster route.
