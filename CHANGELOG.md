# Changelog

All notable changes to cob-rag-engine. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow

## [Unreleased]

## [0.2.0] — 2026-11-12

The first public release, open source under AGPL-3.0. Tested by the automated suites; the newest
parts (payments, WhatsApp answers, the public website, the installer) have not yet had a full live
run on a fresh server, and payments and WhatsApp were tested against simulated providers only.

<!-- OS open source -->
### Open source under AGPL-3.0

- **Changed: cob-rag-engine is open source.** The engine and the dashboard are under the GNU AGPL-3.0.
  The client libraries in `clients/` and the website widget scripts are under the MIT licence. A company
  that does not want the AGPL-3.0 conditions can ask Callobuzz for a commercial licence at
  https://callobuzz.com/contact. Contributions are made under `CLA.md`.
- **Removed: the licence system.** There is no purchase code, no activation, no evaluation copy and no call
  to a licence server. Every feature works for everyone: billing and wallets, WhatsApp (at a public
  address), branding, and any number of businesses. The dashboard has no Licence page or banner. The table
  `license_state` is dropped by migration `phase21_001`. Old `license.*` audit entries stay readable.
- **Upgrading: billing may switch on.** If your copy was a Regular licence or was never activated, customer
  billing was off even with `RAG_BILLING_ENABLED=true`. After this upgrade it is on. If you do not charge your
  businesses, set `RAG_BILLING_ENABLED=false` in your settings file (`/opt/cob-rag/` on a server) before you upgrade.
- **Changed: "Powered by" is a Branding switch.** The line "cob-rag-engine by Callobuzz" is shown by
  default, as plain text, and the operator can hide it under Branding.
- **Removed: the Envato release package.** `scripts/release/`, its CI job and its tests are gone. The
  installer (`deploy/install.sh`) and the setup wizard ask two questions, your web address and your
  e-mail, and no purchase code. `deploy/upgrade.sh` takes a release zip or a folder (for example a
  `git clone`).
- **Changed: support.** Community support runs through GitHub issues, best effort. Commercial support is by
  contract. The security promises in `SECURITY.md` are unchanged.
- **Changed: the public site.** The pages in `docs/` (GitHub Pages) share one stylesheet and one theme
  script (`docs/assets/site.css`, `docs/assets/theme.js`) with the dashboard's colours and fonts. Light is
  the default; a switch in the nav turns on dark and remembers it. The landing page is rewritten for the
  product as it is today (payments, GST invoices, WhatsApp answers, the public website, the installer), with
  a tour of real dashboard screens in both themes; the README opens the same way. Dashboard screenshots are
  regenerated by `DOCS_SCREENSHOTS=1 pnpm e2e --project docs-screenshots`, which now also shoots billing,
  leads and the website editor.
- **Changed: cob-rag-mcp is MIT**, like the client libraries.
- **Added: project files for contributors.** `CODE_OF_CONDUCT.md`, issue forms and a pull request
  template, and `tests/unit/test_public_repo.py`, which keeps env files, `docs/internal/`, scratch files and
  store links out of the repository.

### Businesses choose and change their own plan

- **Added: self-service plans.** A plan has *Businesses can choose this plan themselves* (`plans.self_service`,
  off for every existing plan; the seed command marks the Free, Standard and Pro it creates). Owners see
  **Change plan** on Plan & billing with each plan's fee, the total with GST, what it includes and what a move
  costs today. Moving up starts at once and takes only the difference for the days left in the period from the
  balance (one ledger entry, `plan-change:<workspace>:<plan>:<period start>`, integer paise rounded down, with
  the matching share of the larger included credit); when the balance cannot cover it the move waits up to 7
  days for a payment (online, or a top-up request) and applies as soon as the money arrives. Moving down starts
  at the next renewal through the existing pending-change pass, with no refund. An owner's move is the
  business's own request, so the price-change notice wait does not apply (the audit row says so). New routes
  `GET /api/v1/billing/plans`, `POST /api/v1/billing/plan`, `DELETE /api/v1/billing/plan/pending` (owners;
  refused on a demo) and `GET /api/v1/public/plans`; audit actions `billing.plan_change_applied`,
  `billing.plan_change_awaiting_payment`, `billing.plan_change_scheduled`. With billing off only plans with no
  fee can be chosen (409 `plan_change_needs_billing`).
- **Added: choose a plan at sign-up.** The pricing page's buttons link to `/signup?plan=<slug>` (**Start free**,
  **Start with Pro**); the sign-up form shows the plan with its price, and it applies when the workspace is
  created (a plan with a fee waits for the owner's payment, nothing is charged before; in approval mode it
  applies when the workspace is activated, unless the operator picks another plan). An unknown or
  non-self-service plan starts on the default plan. Migration `phase20_002` (`plans.self_service`,
  `tenants.requested_plan_id`).

### P1 Online payments

- **Added: online payments with Razorpay** (off by default; `RAG_PAYMENTS_PROVIDER`, `RAG_RAZORPAY_KEY_ID`,
  `RAG_RAZORPAY_KEY_SECRET`, `RAG_RAZORPAY_WEBHOOK_SECRET`, or the keys saved encrypted on **Billing →
  Payments**). A business adds money, pays its plan fee or buys an add-on with UPI, a card or net banking on
  the new `/pay` page (the only page that loads Razorpay's checkout, with its own CSP), and a captured payment
  becomes exactly one balance entry keyed `rzp:<payment id>` whichever of the checkout confirmation, the signed
  webhook, the five-minute sweep or the nightly check sees it first. New tables `payment_provider_settings`,
  `billing_profiles`, `payment_orders`, `payments`, `payment_events`, `payment_refunds` (`phase19_001`).
- **Added: GST on every payment.** The balance gets the amount before GST; CGST + SGST in the seller's state,
  IGST elsewhere, none without a GST number. Workspace tax details (`GET/PUT /api/v1/billing/tax-details`, GSTIN
  checked) and the deployer's company details and seller tax profile (`/api/v1/admin/company`,
  `/api/v1/admin/billing/tax-profile`).
- **Added: refunds from unused balance** (`POST /api/v1/admin/billing/payments/{id}/refunds`): the balance entry
  is committed before the provider is called, a refusal puts the money back, promotional credit is never
  refunded. **Payment links**, payment and delivery lists, retry of a failed delivery.
- **Added: webhook** `POST /api/v1/public/payments/razorpay/webhook` (HMAC over the raw body, stored by event id,
  200 at once; a worker asks Razorpay what really happened, so a forged amount or an out-of-order event moves no
  money) and the new `billing.payment_received` webhook event.
- **Added: nightly check R6** against Razorpay's settlement report (a lost webhook is healed and reported;
  amounts that differ are reported, never auto-fixed) and the gateway fee as a cost in the P&L.
- **Changed: `add_on_grants.payment`** also allows `gateway`; credit packs paid online count as collected cash.

### P2 GST tax invoices

- **Added: a GST tax invoice for every captured payment**, written in the same transaction as the balance entry
  (`billing/payments/capture.apply_captured` -> `billing/invoicing/documents.issue_invoice`), so a number is never
  skipped and an invoice always matches the money. Numbers are `PREFIX/YY-YY/NNNNN` (`INV/26-27/00001`), one
  gap-free series per financial year (April to March, Indian time) taken from a row-locked counter
  (`numbering.next_number`). Every Rule 46 field is stored (seller and buyer copied at issue, place of supply, SAC,
  CGST + SGST or IGST, total, "reverse charge: no"). A seller without a GST number issues a **bill of supply**;
  an export under a valid LUT carries the standard wording and no tax. New tables `tax_documents` (frozen by a
  database trigger: only the PDF key, its SHA-256 and the e-mail stamp may be filled in once; never deleted; no
  tenant foreign key) and `tax_document_counters` (`phase19_003`).
- **Added: credit notes** when a refund is processed (`CN/26-27/00001`): the negative of the refund's own tax split,
  naming the original invoice. After 30 November following the invoice's financial year no credit note is issued
  (`payment_refunds.credit_note_skipped`); the refund dialog warns beforehand and the operator is e-mailed.
- **Added: the PDF** (reportlab, A4, bundled Noto Sans for the rupee sign; the amount in words in lakh and crore)
  written once to `billing/tax-documents/<fy>/<id>.pdf` after the commit by `callobuzz_rag.render_tax_document`,
  retried every ten minutes by `callobuzz_rag.sweep_tax_documents`, and announced by the new `invoice_issued`
  e-mail. A PDF that cannot be written never undoes the money.
- **Added: owner and operator screens and routes**: `GET /api/v1/billing/invoices` (+ `/{id}/pdf`) for an owner;
  `GET /api/v1/admin/billing/invoices` (filters and totals), `/export?start&end` (CSV for the accountant, at most
  366 days), `/{id}/pdf` and `POST /{id}/resend` for the operator. **Plan & billing -> Tax invoices**,
  **Billing -> Invoices**.
- **Added: GST-inclusive totals** next to every price an owner sees (plan fee, price list, add-ons) and an
  inclusive hint in the pricing editor; `GET /api/v1/billing/account` gains `gst`, a quote says whether it makes an
  `invoice` or a `bill_of_supply`.
- **Added: check R7** in the nightly books check: every captured payment has one invoice, every processed refund a
  credit note or a recorded reason. New audit actions `billing.invoice_issued` and `billing.credit_note_issued`.
- **Added dependency: `reportlab`** (BSD) and the Noto Sans font (SIL OFL 1.1). E-invoicing (IRN) is not built: it
  is needed only above Rs 5 crore turnover.

### P3 Legal pages

- **Added: eight legal pages** (Terms, Privacy Notice for India's DPDP Act 2023, Refund and Cancellation,
  Shipping and Delivery, Acceptable Use, Data Processing Addendum, Sub-processors, Grievance Officer) as
  shipped templates the operator edits in the dashboard (**Legal pages**, `/admin/legal`) and publishes as
  numbered versions. Each template is marked as needing a lawyer's review and publishing needs a
  confirmation; a page that uses a detail that is not set cannot be published. Published versions are frozen
  by a database trigger. Off by default: nothing is public until published.
- **Added: public pages.** `GET /legal/<page>` is plain HTML with a strict Content-Security-Policy, and
  `GET /api/v1/public/legal` and `GET /api/v1/public/legal/<page>` are JSON. The proxy sends `/legal/*` to
  the engine. New tables `legal_documents` and `legal_acceptances` (`phase19_002`).
- **Added: sign-up records the accepted Terms and Privacy versions** when both are published
  (`accept_legal` on `POST /api/v1/auth/signup`; 422 `legal_acceptance_required`, 409
  `legal_version_changed`); the operator lists who accepted what and downloads a CSV
  (`GET /api/v1/admin/legal/acceptances`).
- **Added: links where people look.** The published pages are linked in the sign-in, sign-up and signed-in
  footers (`legal` on `GET /api/v1/public/branding`), and the chat widget's footer shows a Privacy link
  (`privacy_url` on `GET /api/v1/widget/config`): the business's own policy, else the operator's Privacy
  notice. The lead consent notice's link follows the same rule.
- **Added: a safe Markdown renderer** (`markdown-it-py`, now a direct dependency): no raw HTML, a short list
  of link schemes, `rel="nofollow noopener"` on every link.

### P5 Plans for a hosted service

- **Added: a plan says whether its businesses may use their own AI key** (`plans.byok_allowed`, `phase19_004`).
  It is on for every plan that existed, so an upgrade changes nothing. Without it a business cannot save a key
  (403 `byok_not_in_plan`); a key saved earlier is kept but not used: answers fall back to the operator's model
  and key and the business's balance, a key or address sent with a request is ignored, and COB, the Content
  Portal and the consumption view follow. One module decides (`billing/byok.py`); the answer path reads it in the
  same query as the pipeline profile (`EffectiveProfile.byok_allowed`).
- **Added: two add-on kinds.** `feature_unlock` (the own AI key, for a month or for good, optionally renewing)
  and `service` (installation help, website design, priority support; optional months of support and a SAC
  code for the tax invoice). New fields: `renews`, `sold_to_owners`, `placeholder`. A feature the plan already
  gives cannot be bought (409 `feature_already_included`).
- **Added: renewing add-ons** are charged again from the balance each period under their own key (hourly
  schedule, each missed period once). A balance that cannot cover it ends the add-on and e-mails the owners;
  it never pauses a workspace.
- **Added: service orders** (`service_orders`): buying a service opens an order and a support request;
  the operator moves it requested -> in progress -> done or cancelled with a note the owner reads and an
  internal note they never see; owners are e-mailed on every move. Cancelling refunds nothing by itself.
- **Added: an add-on shop for business owners** on Plan & billing (`GET /api/v1/billing/add-ons`, buy from the
  balance, cancel a renewal, or pay online through the existing pay page), with the total including GST.
- **Added: `python -m callobuzz_rag.billing.seed_saas`** (dry run by default, `--apply`) makes Free, Standard and
  Pro with placeholder prices and a starter set of add-ons; it never changes what exists. Placeholder prices
  carry a badge until edited.

### L5a Demo mode

- **Added: demo mode** (`RAG_DEMO_MODE`, off by default) for a public demo of the product, such as the live
  preview on a CodeCanyon listing. The sign-in page shows two sign-ins, one for the platform owner and one
  for the owner of Nirmal Family Clinic, a made-up clinic in Pune with an assistant that answers in English
  and Hindi. A banner says some actions are switched off.
- **Added: what a demo refuses.** Deleting, API keys, e-mail settings, WhatsApp, the licence, billing
  top-ups, plans, webhooks, password and e-mail changes and signing up all answer one friendly sentence
  (`demo_read_only`). A route added later is refused by default, because the rule follows each route's own
  permission class. Demo mode never changes the licence.
- **Added: nothing leaves a demo.** No e-mail, WhatsApp message or webhook is sent.
- **Added: a daily ceiling on model calls** (`RAG_DEMO_MODEL_CALLS_PER_DAY`, default 1200) on top of the
  demo plan's limits. When the counter cannot be read, the demo stops answering instead of spending.
- **Added: daily answer limits for a demo.** `RAG_DEMO_ANSWERS_PER_DAY` (default 300) is a hard limit for the
  whole demo and `RAG_DEMO_ANSWERS_PER_VISITOR_PER_DAY` (default 15) one for each visitor, so one person cannot
  use it all. A visitor is a keyed hash of the client address (the widget's trusted-proxy logic) plus the
  signed-in user; no address is stored, and people behind one office address share a quota. Only answers that
  call the model count (not small talk, cached answers or requests for a person), on the widget, the
  playground and preview, conversations and COB. Over a limit, or when the counters cannot be read, the visitor
  reads a polite assistant message with the reset time in UTC and IST ("come back tomorrow"), with no model
  call and nothing metered, never an error (the old paths answer 429 `demo_limit` or 503 `demo_unavailable`
  with the same sentence). The dashboard banner and the sign-in page show "X of Y demo answers left today";
  the numbers are in `GET /api/v1/public/branding` (`demo.answers`) and `GET /api/v1/admin/demo`. A demo day
  now starts at `RAG_DEMO_RESET_AT_UTC`, so the limits start again exactly when the demo resets. The default
  of `RAG_DEMO_MODEL_CALLS_PER_DAY` is now 1200 (was 1500).
- **Added: a nightly reset** (`RAG_DEMO_RESET_AT_UTC`, default 21:30 UTC, which is 03:00 in India) that puts
  the demo back to the seed, and fills a new demo server the first time it starts. Two admin routes
  (`GET /api/v1/admin/demo`, `POST /api/v1/admin/demo/reset`) and a command line
  (`python -m callobuzz_rag.demo status` and `reset --wait`) show and start it.
- **Added: `RAG_FRAME_ANCESTORS`**, the list of sites that may show the dashboard in a frame. Empty keeps the
  old behaviour (only the dashboard's own address). A bad value stops the dashboard with a message naming
  the setting.
- **Added: new settings** `RAG_DEMO_MODE`, `RAG_DEMO_PASSWORD`, `RAG_DEMO_OWNER_EMAIL`,
  `RAG_DEMO_RESET_AT_UTC`, `RAG_DEMO_MODEL_CALLS_PER_DAY`, `RAG_DEMO_ANSWERS_PER_DAY`,
  `RAG_DEMO_ANSWERS_PER_VISITOR_PER_DAY`, and new error codes `demo_read_only`, `demo_mode_off`,
  `demo_reset_running`, `demo_unavailable` and `demo_limit`.
- **Added: "Run a public demo"** in the deployment guide.

### L5a Envato package

- **Added: `scripts/release/build_envato.py`**, which builds `dist/cob-rag-engine-<version>-envato.zip` from

  inside: licence text that is not ours, our product called something it is not, `docs/internal`, a private
  key, a real settings file, the licence TEST key, a link to a store or to the code repository, placeholder
  licence keys, a missing changelog entry, a Dockerfile whose files do not reach its build, or a
  documentation page that would make a request off the buyer's disk. The same gates run on every push.
- **Added: offline documentation.** `documentation/index.html` opens from the disk with no internet and no
  fonts or scripts from elsewhere. It is made from the same pages that are published online.
- **Added: the Getting started and Support pages** (`docs/getting-started.html`, `docs/support.html`): a
  beginner's path from the zip to a first customer, and what support covers.
- **Added: `SUPPORT.md`**, and a new **`SECURITY.md`** reporting process with acknowledgement and fix times

- **Added: a checker for the CodeCanyon item-page copy** (title, tags, no price, no store links).
- **Fixed:** the engine image could not build, because `docs/requirements.html` was excluded from its build

- **Changed:** the benchmark tables the dashboard shows link to the public benchmarks page instead of the

### L3b Licence server

- **Added: the licence server** (`cob-licence-server`, a separate private repository that is never shipped
  to buyers). It checks a purchase code with Envato, keeps one live copy per code (and one staging copy
  on an Extended licence), signs the licence, re-signs it weekly, answers a moved, copied or refunded
  copy with a signed notice, tells licensed copies when a new version is out, and has a self-service
  reset page for buyers whose old server is gone. When it is unsure it answers "try later", never a
  refusal. An end-to-end test runs this engine's own licence client against it.
- **Added: `scripts/set_licence_public_key.py`**, which writes the licence server's public keys into
  `licensing/keys.py` after the key ceremony (it refuses the test key), and a test that fails if a
  private key is ever committed.
- **Added: a staging copy on a Regular licence gets its own plain refusal** ("A staging copy needs the
  Extended licence. Activate this copy as your live server instead.") instead of "in use on another
  website". The Move dialog links to the licence server's reset page.
- **Docs:** the COB page "The licence" now says what the licence server keeps, and where to free a code.

### L4 Install and upgrade

- **Added: `deploy/install.sh`**, a one-command installer for a fresh Ubuntu 22.04/24.04 or Debian 12
  server. It checks the server (processors, memory, disk, ports 80 and 443, the operating system),
  installs Docker from Docker's own repository if it is missing, asks three questions (web address,
  e-mail, purchase code), writes the settings with the setup wizard (inside a throwaway Python
  container) with generated secrets, builds and starts the stack, waits until it is healthy, prints
  the sign-in link and sets up a nightly backup. Everything lives in `/opt/cob-rag/`. Running it again
  changes nothing that works; another version installed there points to `upgrade.sh`. `--dry-run`
  prints every step and changes nothing.
- **Added: one public address with automatic HTTPS.** A `caddy` service (compose profile `proxy`,
  `deploy/caddy/Caddyfile`) serves the dashboard at `/`, the engine under `/api/` (plus `/widget.js`
  and the lead-withdrawal pages) and the crawler under `/scraper/`, with a free Let's Encrypt
  certificate. New settings `RAG_SITE_DOMAIN`, `RAG_ACME_EMAIL`, `RAG_PROXY_BIND_ADDR`,
  `RAG_CADDY_IMAGE` (read by compose and the wizard only). The setup wizard derives every address,
  the CORS lists, proxy trust and production mode from `RAG_SITE_DOMAIN`, and refuses an IP address,
  a port or a `.local`/`.test` name as the address.
- **Added: `deploy/upgrade.sh`** (backup, new version beside the old one, build, settings update,
  migrate, switch, health check; one printed command on failure), **`upgrade.sh --rollback`**,
  **`deploy/backup.sh`** (database, uploaded files, crawler data, search index snapshots, settings;
  checksums; the last 7 days kept) and **`deploy/restore.sh`** (checks the checksums, refuses a backup
  from a newer version, asks for the typed word `restore`).
- **Added: `python -m callobuzz_rag.vectordb.snapshots create|restore DIR`**, Qdrant snapshots of every
  collection to a folder and back, checksum-verified.
- **Added: the public requirements page** (`docs/requirements.html`: server sizes with and without the
  free local model, operating systems, network, what is not in the price, not shared hosting) and an
  installer section in the deploy guide.
- **Tests:** the install scripts are checked with shellcheck and run (dry runs, refusals, the pure
  functions) in throwaway `ubuntu:24.04` containers; the Caddyfile is adapted and validated by Caddy
  itself; CI has a "Deploy scripts" job. A real run on fresh servers is part of L6.

### L1 Closed-source switch

- **Changed: proprietary licence.** `LICENSE` is a short proprietary notice that defers to the Envato
  Market licence the buyer bought (Regular or Extended). Package metadata (`pyproject.toml`, both
  client SDKs), the widget scripts, the README, CONTRIBUTING and the docs no longer use open-source
  licence wording. `CLA.md` and its workflow are retired.
- **Added: `THIRD_PARTY_NOTICES.txt`**, generated by `scripts/third_party_notices.py` from the
  installed Python packages (engine and scraper), the dashboard's production packages and
  `third_party/services.toml`; `--check` fails when it is out of date.
- **Changed: "Powered by" is plain text.** "cob-rag-engine by Callobuzz" stays on the widget, e-mails,

### BIZ2 Keeping a website fresh

### BIL3: wallet ledger and charging

### Named keys, permissions and delete guardrails

- A knowledge base, a workspace and the engine can each hold several **named keys** with a
  permission (`read`, `write` or `full`); the old single keys become each one's "Default key".
  A key can no longer create a knowledge base with more permission than it holds: the new
  knowledge base's Default key is capped at the creating key's permission.
- Faster key verification for installs upgraded from single keys: a named key is checked before the
  migrated Default key, so it costs one bcrypt instead of two.
- Deleting with an API key needs `confirm_name`; the delete-preview routes say what would go.
  The dashboard has a **Connect an agent** panel that makes a read key named for the client.

### Smart ingestion and documents with no text

- Replacing a document deletes the retired version's vectors after the job's commit, not before. A
  Qdrant failure there is logged and no longer rolls back the new version.
- A workspace member can no longer reset an owner's page-stripping choice by sending
  `retrieval_config: null` (403 `owner_required`).
- `reindex --rehash-blocks` seeds only documents that have no paragraph-hash rows yet, so exact
  hashes from newer ingests are not overwritten.
- The near-duplicate check leaves out chunks made only of paragraphs other documents of the
  knowledge base hold, so short pages of one site no longer wait in `pending_review` because of a
  shared menu and footer.
- A file that parses to no readable text fails with `no_text_found` and a plain sentence.
- `benchmarks/documents.py` pages through documents at the API's 100-per-page cap.

### Proxy addresses, e-mail checks and faster answers

- A rate limit, timeout or bad key on a thinking-effort call no longer switches thinking off for
  that model until restart. Only an error about the parameter itself is retried and remembered.
- Helper calls (rewrites, classification, LLM re-ranking) ask for the cheapest thinking the provider
  supports, and a knowledge base's answer effort never reaches a different model.
- X-Forwarded-For padding can no longer hide a caller's real address: only the last

- A legacy `RAG_WIDGET_TRUST_PROXY_HEADERS` in an existing environment file is carried to

- Sign-in, forgot and reset check the e-mail shape only, so `.local` and `.test` accounts can still

### Strict request bodies everywhere

- Every request body model now rejects fields it does not declare: unknown fields are a **422**
  with FastAPI's `extra_forbidden` entry, whose `loc` ends in the field (and starts with the
  nested path, e.g. `body.records.0.titel`). 33 request models ignored them silently (for example
  `CreateCorpusRequest`, `WebhookCreateRequest`, `WorkspaceCreate`), plus the config and record
  objects nested in them. One shared base class, `core.schemas.StrictRequest`, carries it. Response
  models are untouched.
- The startup audit (`api/schema_strictness.py`) stays and now also walks nested models; it reports
  zero permissive bodies, and a unit test fails if a new request model is added without
  `StrictRequest`.
- The Python and JavaScript SDKs, cob-rag-mcp and the dashboard send only declared fields. Each now
  has a test that checks every body it sends against `docs/openapi.json`. A client that sent an
  undeclared field (a typo, or a field of another version) now gets the 422 instead of a silent
  no-op.

- `RAG_APP_NAME` now defaults to `cob-rag-engine` (was `callobuzz-rag`), in `core/config.py` and

### Plan setting: count cached answers

- `plans.count_cached_answers` (bool, default true; migration `phase11_011`; in the plan API and the
  dashboard's Plans dialog and cards). `POST /query` answers from the query cache skipped the usage
  meter, so the monthly question counter never saw them. With the setting on, a cached answer now
  counts as a question (`record_usage`, `tenant_question_counts`) and a tenant at its cap is
  refused it with 429, like any answer. With it off, cached answers are free: not counted, and
  still served at the cap. A cache miss is always capped and counted.

### Restoring a version is all-or-nothing

- `POST /documents/{id}/versions/{version_id}/restore` used to retire the active version and
  delete its vectors BEFORE checking that the old version had chunks, so a 422 (or an embedding or
  vector-store failure) rolled the database back but left the document with no vectors. It now
  validates first (the version exists, belongs to the document, has chunks, the embedder works),
  writes the restored version's vectors while the current version's are still in place (also into a
  running embedding migration's collection), commits the database, and only then deletes the
  previous version's vectors. On any failure before the commit the restored version's partial
  vectors are removed and the current version stays active and searchable.

### Upload limits count real text

- The request now checks only a byte cap, `RAG_MAX_UPLOAD_BYTES` (default 50 MB): over it is a
  **413** `upload_too_large` with `limit_bytes` and `size_bytes`. The old "bytes divided by 4"
  token estimate on the raw file is gone, so a 5 MB PDF is no longer refused for its size.
- The token cap, `RAG_MAX_DOCUMENT_TOKENS` (default 500,000), is enforced by the pipeline after
  parsing, on the parsed text's real token count (the chunker's tokenizer). A document over it
  fails its job before chunking with `document_too_large` (`tokens`, `limit`) in the job's
  `errors`, and its staged file is deleted.
- Plans may set lower caps: `plans.max_upload_mb` and `plans.max_document_tokens` (NULL = the
  engine's; migration `phase11_010`), in the plan API, the Plans dialog, plan cards, and the
  tenant's Plan page. A plan cannot raise the engine's limits.
- `GET /api/v1/info` `limits` reports `max_upload_bytes` and the new `max_document_tokens` (it
  replaces `max_upload_tokens`), both as the caller's effective caps. The dashboard's Add content
  hint shows both instead of a bytes/4 estimate.

### Skip a near-duplicate upload

- `POST /api/v1/ingest/{job_id}/confirm` takes a third action, `skip` (alias `discard`): the
  upload held for review is dropped at once. The job becomes `skipped` (a new job status, also a
  `GET /ingest/jobs?status=` filter), its stored file is deleted and nothing is indexed. Skipping
  twice returns the same answer; a decided or expired review is the usual 409 / 410. Members may
  skip, like replace and keep both. The dashboard's "Possible duplicate" card has a
  **Skip (don't add)** button.

  bootstrap's refusal. Deleting the workspace on purpose is remembered
  (`operator_workspace_removed`) so a restart does not recreate it; `bootstrap
  --restore-operator-workspace` does.
- **Protection.** Suspending it (`POST .../suspend` or `PUT is_active:false`) is 409
  `operator_workspace_protected`. `DELETE /api/v1/admin/tenants/{id}` needs the typed name and
  `?confirm_operator_workspace=true` (422 `operator_confirmation_required` otherwise). The Internal
  plan cannot be edited, deactivated or deleted (409 `plan_internal_locked`) and only the operator
  workspace can be put on it (409 `plan_not_assignable`); `GET /api/v1/admin/plans?include_inactive=false`
  (the picker) leaves it out. New audit actions: `operator_workspace.created`,
  `operator_workspace.suspend_refused`, `operator_workspace.delete_refused`; its deletion is a
  `tenant.deleted` row with `operator_workspace: true`.
- **The super admin inside it.** `POST /api/v1/auth/switch-tenant` from a super-admin session now
  accepts the operator workspace (and only it; any other tenant is still 403 `not_member`): the
  session becomes a plain workspace session, role owner, through the same `resolve_scope` /
  `authorized_corpus_ids` as any tenant, so it cannot reach an admin route. New
  `POST /api/v1/auth/switch-admin` goes back (403 `not_superadmin` for anyone else). Login accepts
  the workspace as `tenant_id`, refresh keeps it, and a token naming any other tenant for the super
  admin fails closed (403 `not_member`).
- **Reports.** `GET /api/v1/admin/tenants` takes `is_operator` (`false` = customers only);
  `GET /api/v1/usage` rows grouped by tenant carry `is_operator`, and `exclude_operator=true` leaves
  the workspace out of any grouping. Usage metering and the monthly question counts are untouched.
- **SDKs.** `list_tenants(is_operator=...)` / `listTenants({ isOperator })` and
  `delete_tenant(..., confirm_operator_workspace=True)` / `deleteTenant(id, name, {
  confirmOperatorWorkspace: true })`; `usage(exclude_operator=...)` already forwards parameters.

### Setup wizard: the GPU is asked once

summary shows where each local model runs. Previously the GPU was asked a second time after
choosing the local re-ranker.

### Docker footprint renamed

The compose project is now `cob-rag` (was `callobuzz-rag`): containers are `cob-rag-app-1`,
`cob-rag-postgres-1` and so on, images are `cob-rag:local`, `cob-rag-scraper:local` and
`cob-rag-dashboard:local`, and the named volumes and network follow the project name. The Python
package `callobuzz_rag` and the compose service names (`app`, `worker`, ...) are unchanged.

**Upgrading.** An existing install gets new, empty volumes under the new name, so its data does
not carry over: move the old volumes' data across, or start fresh (`docker compose down -v` under
the old name, then `docker compose up -d --build`).

### Compose: ports, scraper origins, TEI only when used

- The host ports of the engine (8000), scraper (8001) and dashboard (8090) are now
  `RAG_APP_HOST_PORT`, `RAG_SCRAPER_HOST_PORT` and `RAG_DASHBOARD_HOST_PORT`, still bound to
  `RAG_BIND_ADDR`. `python scripts/setup.py --full` (or `make setup ARGS="--full"`) asks for them and moves the matching addresses.
- The scraper's CORS origins come from `SCRAPER_CORS_ORIGINS` in `.env` (default: the dashboard's
  origins); `make setup` writes it from the dashboard address and port.
- The bundled TEI container is behind a new `tei` profile, on in the default `COMPOSE_PROFILES`
  (`local-storage,tei`), and the app only waits for it when it runs. Choosing a hosted embedding API
  or in-process embeddings in `make setup` drops the profile, so TEI neither starts nor downloads its

**Upgrading.** Add `tei` to `COMPOSE_PROFILES` in your `.env` (`local-storage,tei`) if you use the
bundled embedder, or re-run `make setup` (it adds or drops it from your embedding choice). Without
it TEI no longer starts.

  the legacy dashboard.

### Fixed — API correctness
- **Golden-set CSV import read an Excel file as empty.** `POST /api/v1/golden/import` opened the
  upload as `utf-8`, so a byte-order mark (Excel's "CSV UTF-8") made the first header
  `﻿query` and every row was skipped: 0 imported, no error. It now reads `utf-8-sig`.
- **A bad `expected_chunk_ids` value in a golden import was a 500.** It is now a 422 whose
  `detail` names the row (as a spreadsheet numbers it) and the value, and nothing from the file
  is imported.
- **`memory_type` is checked everywhere it is accepted.** Create and bulk create already
  refused an unknown kind; the list filter answered it with a 400 and bulk delete accepted any
  string (and deleted nothing). All four now take only `fact`, `preference` or `entity`, the
  kinds extraction produces (`MEMORY_TYPES` in `db/models/memory.py`), and answer anything else
  with a 422. OpenAPI lists them as an enum.
- **Analytics trends accepted any `granularity`.** `GET /api/v1/analytics/queries/trends` passed
  it straight to `date_trunc` (as a bound parameter, never interpolated), so `year` worked by
  accident and a typo was a database error, a 500. Only the documented `hour`, `day`, `week` and
  `month` are accepted; anything else is a 422, and `QueryStatsService.get_trends` refuses it too.
- **The eval and optimization run lists are typed.** `GET /api/v1/admin/eval/runs` and
  `GET /api/v1/admin/optimize/runs` returned an untyped page; OpenAPI now documents their items
  (`EvalRunListResponse` of `EvalRunSummary`, `OptimizationRunListResponse` of
  `OptimizationRunSummary`). The payload is unchanged.
- **An engine-wide retrieval override could not be reset.** `PUT /api/v1/admin/config/retrieval`
  stored a field sent as `null`, and the next `GET` then failed validation. `null` now removes
  that override, as in corpus-level config: the engine default applies again, other overrides
  stay, and `source` reads `defaults` once none remain. A `null` stored earlier reads as the
  default. No default or retrieval behaviour changed.
- **A webhook test that timed out was a 500.** `POST /api/v1/webhooks/{id}/test` mapped only
  status and connection errors to 502. Every `httpx` error (timeouts, protocol and redirect
  errors) is now the same 502, with `detail` `Webhook delivery failed: <error class>`; the raw
  message, which can name internal addresses, is not returned.
- **The portal audit trail was a 500 once a chunk had been split, merged, approved or
  rejected.** Those entries store `details` as an object, and `AuditTrailEntry.details` was typed
  a string; entries the AI chat wrote had no timestamp, which the model required.
  `GET /api/v1/portal/workspaces/{id}/audit-trail` now types `details` as an object (a string on
  older entries) and `timestamp` as nullable (those entries sort last); the AI chat's older
  top-level extras (`source_chunk_id`, `source_chunk_ids`) come back inside `details`, and it now
  writes entries in the editor's format, with a timestamp.
- **The portal workspace list had no counts.** `GET /api/v1/portal/workspaces` returned null
  `content_count`, `chunk_count` and `approved_chunk_count`. They are filled for the whole page
  with one grouped query (the single-workspace `GET` uses the same query instead of three).
- **Portal review refusals carry their code.** Submit, approve, reject and ingest on a workspace
  in the wrong status answer 409 `invalid_status_transition` (was an uncoded 409). The
  maker-checker refusal (the creator approving their own workspace) stays a plain 403: the code
  catalog has no code for it.
- **`review_exists` names the open review.** The 409 from
  `POST /api/v1/portal/workspaces/from-ingestion` now carries the existing review workspace's
  `workspace_id`.
- **The request-strictness audit at startup had gone silent.** Under FastAPI 0.14x `app.routes`
  holds one wrapper per included router, with no `endpoint`, so the audit inspected no route and
  logged nothing. It now walks included routers at any depth, resolves the string annotations of
  modules using `from __future__ import annotations` (the query routes), and skips `Depends`
  parameters such as the engine `Settings`. It again logs the strict request bodies at INFO and
  the ones that still drop unknown fields at WARNING; no model's behaviour changed.
- **The document limit counts queued ingests and holds under concurrency** (accounts A6). Two
  record imports a second apart could both pass a `max_documents: 1` limit, because the check
  counted only committed documents. Each ingest job now stores how many new documents it will
  add (`ingest_jobs.pending_new_documents`, migration `phase11_007`, backfilled for jobs in
  flight); the check counts active documents plus queued and running jobs' additions under a
  per-tenant advisory lock held until the job is committed, and the 409 carries `queued`. The
  worker re-checks before creating a document and fails the job with `document_limit_reached`
  (with `limit`, `used`, `queued`, `adding`) in its `errors`. Unlimited plans take no lock.
- **Ingest never stored a parent link.** The chunker gives every section it cuts into parts a
  parent chunk holding the whole section, but ingest linked each child to its parent's id before
  the database had assigned one, so every `parent_chunk_id` was NULL (0 of the reference stack's
  273,658 chunks) and parent expansion in conversations and the agent's search tool never ran.
  File ingest, re-ingest and record imports now store the links. Existing documents are fixed by
  `python -m callobuzz_rag.retrieval.reindex --parents` (a dry run; add `--apply` to write),
  which recovers each version's links by the chunker's own rule, touches Postgres only and
  leaves versions that already have links alone. Parent expansion itself stays off by default
  (`HybridSearcher.search(expand_parents=False)`), so conversation and agent results are the
  same as before; with links stored it can now be turned on and evaluated.
- **Retired versions came back after an embedding migration.** While a migration was running,
  re-ingest, record updates, version restore, merge and document delete removed old points only
  from the corpus's own collection, so a version the migration had already copied survived in
  the new collection and was searchable again after cutover; record imports and restores did not
  write their new points there at all. Every change to a version's points now reaches the
  migration's new collection too (best effort, like the rest of dual-write), and ingest's
  dual-written points carry the full payload (category, user_id and custom metadata were lost).
- **A document could end up with two active versions.** Re-ingest and version restore retired
  the active version without locking anything, so two of them racing on one document, or one
  racing a review finalize, could leave two active versions, both searchable. Ingest, record
  imports, restore and merge now lock the document row and re-read its versions first, and a
  partial unique index allows one active version per document (migration `phase10_004`, which
  first keeps only the newest of any duplicates and names the corpora whose collections then
  need `reindex --apply --rebuild`).
- **Upload idempotency keys were global and a retry got a 409.** `idempotency_key` on
  `POST /api/v1/ingest` was unique across every corpus, so one tenant's key clashed with
  another's and the 409 revealed it existed. It is now unique per corpus (migration
  `phase10_005`); a retry with the same key and the same file returns the job it first created
  (also when two retries race), and the same key with a different file is `409`.
- **A task queue outage left jobs `queued` forever.** When the broker refused the dispatch after
  the job was saved, `POST /ingest` and `POST /ingest/records` answered 500 and the job never
  moved. The job is now marked failed (`failed_at_step: dispatch`), its idempotency key released
  and the stored upload removed, and the response is `503`; a confirmation whose dispatch fails
  stays `pending_review` so it can be confirmed again.
- **A corpus whose collection holds another embedding model could not be searched.** Ingest,
  query, retrieve, the widget, conversations, memories and version restore always embedded with
  the engine's default model, even after a migration had moved a corpus to another model's
  vectors (a dimension mismatch, or silently wrong neighbours). They now embed with the model
  the corpus's collection holds (`applied_embedding`), with the corpus's own hosted-embedding
  key; migrations use that key too (the migration snapshot never stores it, so a hosted target
  used to run on the engine's key); the query-embedding cache is keyed by that model; and a
  worker task builds its own provider instead of reusing one bound to a previous task's event
  loop, closing dual-write embedders after use.
- **The nightly drift check queued a no-op re-embed for every corpus created through the API.**
  `POST /corpora` never recorded `applied_embedding`, and the drift check read the empty value as
  "drifted": each such corpus got a `pending_approval` migration onto the very same model.
  Create now records the model, the check treats an empty value as the engine default, and
  migration `phase10_002` backfills the column and cancels those no-op migrations.
- `GET /api/v1/documents/{id}/versions` loaded every chunk of every version (text included) just
  to count them; it now counts in the database.
- **A request after a stream could fail with HTTP 500 "connection is closed".** An SSE client
  closes the connection as soon as it reads `done`; Starlette then cancels the streaming
  response, and `/query/stream`, the widget chat and the conversation stream all still had a
  database write to do (usage metering ran after `done`). Under the auth and widget-CORS
  middlewares, which were Starlette `BaseHTTPMiddleware`, that write was cancelled mid-query and
  its connection went back to the pool dead, so the next request (a `DELETE /corpora/{id}`, a
  second stream) failed. Now every stream saves and meters before its final event and shields
  those writes from cancellation, `/query/stream` and the widget chat release the request's
  session before streaming, the conversation stream runs on a session of its own that is closed
  shielded even when the client leaves mid-answer, both middlewares are pure ASGI, and the
  connection pool pre-pings. Metering a stream is no longer lost when the client hangs up.
- **An LLM provider that never answered held a request open indefinitely.** LiteLLM waits 6000
  seconds by default and the engine set no limit, so one hung call (seen on query understanding
  before a stream) meant no response headers at all. Every call now carries
  `RAG_LLM_TIMEOUT_SECONDS` (default 120; for a stream, the wait for each chunk) and query
  understanding, which a query can do without, `RAG_LLM_FAST_TIMEOUT_SECONDS` (default 30).
- **RAGAS evaluation could not run at all.** In the Docker image `import ragas` failed with
  `No module named 'langchain_community.chat_models.vertexai'`: every ragas release imports that
  module, and langchain-community 0.4.2 deleted it. `langchain-community` is now pinned to
  `>=0.4.0,<0.4.2`. Behind that, the runner called `ragas.evaluate()` with no model, so RAGAS
  wanted an `OPENAI_API_KEY` the engine does not have; it now judges with the corpus's resolved
  LLM (engine default for cross-corpus runs) through LiteLLM and embeds with the engine's own
  embedding provider. Context recall, which needs a reference answer, runs only when every
  sampled question has a golden pair (matched case- and whitespace-insensitively) instead of
  failing the run; context precision is now stored (RAGAS names it
  `llm_context_precision_without_reference`, so it was silently dropped); scores are averaged
  over the samples RAGAS could score instead of read through a method its result type lacks;
  and a run with no LLM credentials, or with no metric scored, fails with a message that says so.
- **A corpus's own stored LLM key was never used.** The query, stream, widget and conversation
  paths built their config resolver from `app.state.encryptor`, which nothing set, so the
  encrypted `llm_config` key could not be decrypted and every call fell through to the engine's
  default key (or none). The API now creates the encryptor at startup (the corpus's own
  embedding key is covered by the entry on per-corpus embedding models below).
- **Conversation messages ignored the corpus's LLM settings and were not metered.** They ran on
  the engine's startup provider, so a corpus's own model, fast model and stored (encrypted) key,
  and the caller's `X-LLM-*` headers, were all skipped. Both the JSON and the streamed
  (`Accept: text/event-stream`) branch now resolve the model and key exactly like `/query`
  (header → corpus key → engine default), the auto-title runs on the resolved fast model, and
  every answer is recorded in usage under the new source `conversation` (the title call adds
  its tokens and cost without counting as another request). Auto-generated titles are now
  actually saved; they were flushed and then rolled back.
- **Admin eval, optimize and gap triggers returned ids you could not poll.** Each returned a
  fresh random uuid unrelated to any row, lists and details always said `corpus_id: null`, the
  optimizer never saved its run at all, and `POST /admin/gaps/trigger` sent a task name no
  worker registers. The API now creates the row first (status `queued`), hands its id to the
  worker, which moves that same row to `running` and then `completed`/`failed`, and returns the
  id to poll. `eval_run` and `optimization_runs` gained a `corpus_id` column (migration
  `phase9_005`), `corpus_id` in trigger bodies must be a UUID of an existing corpus (422/404),
  details include `error_message`, eval details accept the stored metric objects (they failed
  validation), and `POST /admin/gaps/trigger` takes an optional `corpus_id`. A broker outage
  answers 503 and marks the row failed instead of leaving it queued forever.
- **`POST /api/v1/analytics/gaps/run` said 202 but ran synchronously**, holding the request open
  through embedding and BERTopic clustering. It is now queued on the worker like every other
  background job: 202 with the report in status `queued`; poll `GET /api/v1/analytics/gaps/{id}`.
  A corpus key that omits `corpus_id` now runs on its own corpus instead of getting a 400.
- **Corpus config could not be cleared, and `{}` reset it.** `PUT /api/v1/corpora/{id}` and
  `PATCH /api/v1/config` merged with nulls dropped, so a stored LLM key, `base_url`, prompt or
  retrieval override could never be removed, while `retrieval_config: {}` silently reset the
  corpus to engine defaults. Now a field sent as null is removed (the next tier applies again),
  `llm_config.api_key: null` deletes the stored encrypted key, `{}` changes nothing, a whole
  section sent as null resets it, and `description: null` clears the description. An empty-string
  `api_key` is a 422 rather than a guess. Secrets stay redacted in responses, and the retrieval
  bounds are checked on the merged result for both admin and corpus keys.

### Security
- **Query history was readable across clients.** `GET /api/v1/query/{id}` returned any past
  question and answer to any valid key. It is now scoped like every other read (corpus key: its
  own; tenant key: its corpora; admin: all) and answers 404 outside that scope.
- **Feedback was scope-checked for corpus keys only**; a tenant key could rate another tenant's
  answers. `POST /api/v1/feedback` now uses the same scope rules.
- **Deactivating a tenant did not switch off its corpus keys.** A `ck_` key of a deactivated
  tenant is now refused on every request, cached verification included.
- **Content Portal routes had no ownership check**: any valid key could read, edit, approve or
  ingest another client's workspace. Every workspace route now checks the workspace belongs to
  the caller's scope, and review-from-ingestion files the workspace under the document's real
  corpus instead of a random id.
- **Scraper service**: every route now requires an engine key (checked against the engine),
  jobs are visible only to their owner, delivery goes only to the configured engine with the
  caller's key (it used to post pages to the scraped site itself, with an empty key),
  `review_mode: false` delivers automatically, and CORS is limited to the dashboard's origin.
- The isolation benchmark now also attacks query history, feedback and a deactivated tenant's
  keys: 60 of 60 attempts refused (`benchmarks/results/ops-2026-09-29-isolation.md`).
- **Content Portal scoping (accounts epic A0).** Workspaces, staging and content rules took only
  a corpus key (rules had their own hand-written check that refused tenant keys); every portal
  route now authorizes through the engine's one scoping rule, so admin and tenant keys work with
  `corpus_id` (create/list) or the workspace in the path, and another client's workspace or
  corpus is `403`. Workspace list returns the workspaces of every corpus in the key's scope.
- **A chunk could point at another workspace's staged document.** `POST …/workspaces/{id}/chunks`
  took `staged_document_id` from the body unchecked; one from another workspace is now `404`.
- **Actor names are the signed-in user's.** `user` in portal bodies, `?user=` and `X-User-Id`
  are recorded as sent for API keys; for a signed-in session (accounts, coming) the account's
  e-mail is recorded instead, so nobody can lock, edit or approve as someone else. `user` is now
  optional everywhere (it defaults to `X-User-Id`, else `api_key_user`), and bodies that held
  nothing else (lock, unlock, submit, approve, ingest, approve/reject chunk, finalize-review) may
  be left out.
- **Every portal handler checks its workspace itself**, not only the router-level guard; another
  workspace's staged content (reprocess) or chunk (AI chat actions) named inside your own
  workspace is `404` (was `400` / `422`).
- **Post-ingest review finalize is a new document version.** It wrote to a fixed `chunks`
  collection (on older installs a real corpus's), trusted the editable `engine_chunk_id` in chunk
  metadata, and patched the reviewed chunks in place: a rejected parent with an edited child
  failed with a 500, a rejected child's text stayed searchable inside its parent, edited chunks
  kept stale token counts and keywords, and split, merged or added chunks were refused. Finalizing
  now publishes the workspace's accepted chunks (everything not rejected or deleted) as a new
  active version of the reviewed document, with parent chunks re-derived from their surviving
  children and every chunk enriched, embedded and indexed as ingest does, into the corpus's own
  collection (and an embedding migration's dual-write collection). The reviewed version is kept
  inactive, restorable with `POST /documents/{id}/versions/{version}/restore`, and its vectors are
  removed; a failure part-way leaves the document as it was (`503 finalize_failed`). Refusals
  carry a `code`: a review of a version that is not the active one, or a finalize after the
  document changed, is `409 version_not_active`; finalizing an authoring workspace, or approving
  / ingesting a review workspace (which duplicated the document), is `409 wrong_workspace_kind`;
  finalizing twice is `409 invalid_status_transition`, someone else's edit lock `409
  workspace_locked`, everything rejected `422 nothing_to_finalize`. The response reports the new
  version's id and what it holds. Workspaces record `kind`, `reviewed_version_id` and
  `finalized_version_id` (migration `phase10_003`, existing review workspaces backfilled).
  Parent chunks are recognised by the chunker's rule, since ingest has never stored
  `parent_chunk_id`. A finalize after the reviewed document was deleted is `409
  reviewed_document_deleted` (not `version_not_active`), a workspace deleted meanwhile `404`,
  and a version restored after its review was finalized can be reviewed again. Splitting or
  merging a parent chunk in a review published its children's text twice: a parent's copy
  is now only a marker (its text is rebuilt from the children), the chunk editor and the AI
  assistant refuse to edit, split, merge, rewrite or re-point it (`409 parent_chunk_derived`),
  and edits of it made earlier are listed in the finalize response (`discarded_parent_edits`)
  instead of dropped silently. A chunk added in a review joins the parent of the section it
  sits in when it carries that section's heading path. Finalize builds (enriches and embeds)
  before taking any row lock and then waits at most 5 s for the workspace and document rows
  (`409 document_busy`, instead of hanging behind an ingest), re-checking under the locks
  (`409 review_changed` if chunks were edited meanwhile). A commit that fails but did apply
  keeps the new version's vectors instead of removing them.
- **Deleting a corpus never deleted its stored files.** `app.state.object_store` was never set
  and the storage provider had no `delete_prefix`, so uploads (`corpus/{id}/`) stayed in the
  bucket. Deleting a corpus now removes them and the portal's staged uploads (`portal/{id}/`),
  and deleting a draft portal workspace removes its own; the request queues a Celery task per
  folder, bounded (5 s connect, 30 s read, 3 attempts; 5 retries) and never blocking the request,
  and a final failure is an `ERROR` naming the folder. `python -m callobuzz_rag.storage.gc`
  finds anything left behind (see Added).
- **A stored file could outlive its row.** Uploads stored the file before writing its row, so a
  corpus or workspace deleted in between left an orphan; the row is now written first (a delete
  that raced it waits, then cleans the file up), a failed commit deletes the file, a storage
  failure is a `503`, and a reused `idempotency_key` is a `409` instead of a `500`. Portal ingest
  also queued its task before committing the job row; it now queues after.
- The isolation benchmark attacks the Content Portal when it is on (workspace read/edit/delete/
  lock, staged content, chunks, submit/approve/ingest, AI chat, audit trail, rules,
  from-ingestion, and the workspace list), and since the review follow-up also B's review
  (finalize, status), AI chat actions, and B's staged content, chunks and rules named from A's
  own workspace: 209 of 209 attempts refused
  (`benchmarks/results/ops-2026-09-30-accounts-a0-review.md`).

### Added
- **Storage garbage collector.** `python -m callobuzz_rag.storage.gc` lists stored-file folders
  (`corpus/{id}/`, `portal/{id}/`, `portal/{corpus}/{workspace}/`) whose corpus or workspace no
  longer exists, with object counts and sizes; `--apply` deletes them after printing the list.
  Dry run by default; files younger than `--min-age-minutes` (60) and keys outside the engine's
  layouts are left alone. `ObjectStorageProvider` gains `list_objects`.
- **Documents, self-service config, conversations and memories accept admin and tenant keys.**
  They took only a corpus key, so an admin or tenant dashboard would have needed every client's
  `ck_` key, which cannot be read back. Admin and tenant keys now name the corpus
  (`?corpus_id=` on `/documents` and `/config`, the path on `/corpora/{id}/conversations` and
  `/memories`), scoped like every other route: a tenant reaches only its own corpora (another's
  is 403), a corpus key only itself, and a corpus key still needs no `corpus_id`. Admin and
  tenant keys get exactly the corpus key's `/config` view and the same bounds on `PATCH`, whose
  response now includes `corpus_id`.
- `GET /api/v1/tenants/me` and `POST /api/v1/tenants/me/rotate-key`: a tenant key reads its own
  record (name, active, created, corpus count, corpus limit) and rotates its own key without the
  admin key. The new key is shown once; the old one fails on its next request, cached or not.
  Admin and corpus keys get 403 (`get_authenticated_tenant`, unused until now, also answered 401
  to an admin key while its docstring said admin was allowed).
- **Corpus list and detail say who owns a corpus and how busy it is.** Each corpus carries
  `tenant_id`, `tenant_name`, `document_count`, `chunk_count` (chunks of active versions) and
  `last_activity_at` (the later of its last logged query and its last ingest job; two new
  `(corpus_id, created_at)` indexes, migration `phase10_001`, keep that one probe each).
  `GET /api/v1/corpora` takes `?tenant_id=` (a tenant key may name only itself), `offset` and
  `limit` (default 100, max 500) and returns `total`, `offset` and `limit` next to `count`
  (items on the page). The admin key can move a corpus to another tenant with
  `PUT /api/v1/corpora/{id}` `{"tenant_id": ...}` (the target's corpus limit applies; `null`
  detaches it); a tenant key cannot.
- **Ingest jobs say what they are.** Job responses carry `corpus_id`, `file_name`, `mode`,
  `target_document_id`, `expires_at` and, for a job held in `pending_review`, the
  `similar_documents` it resembles (id, similarity, match count and file name), so a review
  screen can show which document an upload looks like. `GET /api/v1/ingest/jobs` takes
  `status`, `corpus_id`, `offset` and `limit` (1-100, was unbounded) and returns `total`;
  `count` stays the page size. Scoping is unchanged, now through the shared rule (another
  corpus's `corpus_id` is 403).
- `GET /api/v1/feedback`: the ratings themselves, newest first, each with its question,
  `query_id` and corpus (so `POST /golden/from-feedback` can be driven from a UI). Filters:
  `corpus_id`, `min_rating`/`max_rating`, `start`/`end`; `offset`/`limit` with `total`. Scoped
  through the rated query's corpus.
- `GET /api/v1/migrations`: embedding migrations across corpora (`corpus_id`, `status`,
  `offset`/`limit`, `total`), so drift-created `pending_approval` rows no longer have to be found
  corpus by corpus. The admin sees all; a tenant now reads its own corpora's migrations here, on
  `GET /api/v1/migrations/{id}` and on `GET /api/v1/corpora/{id}/migrations` (it can start one
  with `PUT /corpora` but could not watch it). Approve, cancel, retry, rollback and approve-all
  stay admin-only. `GET /api/v1/models/embeddings` is readable with any key.
- `GET /api/v1/documents/{id}`: a document with its versions and the chunks of its active
  version (or `?version_id=`), read-only and paginated (`chunk_offset`/`chunk_limit`, 1-200,
  with `chunk_total`); each chunk has its index, text, section, page, token count and table/code
  flags. `GET /api/v1/documents` takes `?search=` (part of the file name or external id,
  case-insensitive, `%`/`_` taken literally) and its items carry `external_id` and `metadata`.
- `GET /api/v1/info` (any valid key): engine version; which features are on (Content Portal,
  streaming, transcription and its provider, local and LLM reranking, web search); the
  embedding and LLM models and whether the engine holds its own LLM key; the public URL; and the
  limits a UI should mirror (upload size and token cap, accepted MIME types and extensions,
  audio only when transcription is configured, records per import, question length). No
  secrets.
- An upload the browser labels `application/octet-stream` is now recognised by extension for
  every accepted type (`.pdf`, `.docx`, `.pptx`, `.png`, `.jpg` were refused as unsupported); the
  magic-byte check still applies.
- `POST /api/v1/corpora` accepts `embedding_config` (a model from
  `GET /api/v1/models/embeddings`, validated like `PUT`, its key encrypted). The new corpus's
  collection is built with that model's dimensions and needs no migration.
- `PATCH /api/v1/webhooks/{id}` `{"enabled": false|true}` pauses or resumes a webhook without
  deleting it and its secret (admin key).
- `PATCH /api/v1/golden/{id}` edits a golden pair (question, expected answer, expected chunk
  ids, metadata; only sent fields change, null clears chunk ids or metadata), scoped like the
  other golden routes. `GET /api/v1/golden` adds `total`, `offset` and `limit` (`count` stays
  the page size).
- SDKs: `whoami()`, `info()`, `own_tenant()` / `rotate_own_tenant_key()`, `list_jobs()`,
  `list_documents()`, `get_document()` (Python, also on `AsyncCobRag` except the rotation) and
  `whoami`, `info`, `ownTenant`, `rotateOwnTenantKey`, `listJobs`, `listDocuments`,
  `getDocument` (JS).
- The isolation benchmark attacks every route admin and tenant keys gained here (documents,
  document detail, config read and write, conversations, memories, job and feedback lists,
  migrations list/detail/approve, golden edit, corpus list by tenant, moving a corpus) and checks
  nothing changed: 112 of 112 attempts refused
  (`benchmarks/results/ops-2026-09-29-dashboard-e0.md`).
- Companion package **[cob-rag-mcp](https://github.com/callobuzz/cob-rag-mcp)**: an MCP server
  (stdio and streamable HTTP) and the `cob-rag-engine` CLI for any self-hosted engine. A key only
  sees the tools its kind may use; destructive tools are off unless enabled. Its types are
  generated from `docs/openapi.json`, which is now committed and kept current by a unit test.
- `GET /api/v1/whoami`: tells any admin, tenant or corpus key what it is and which tenant and
  corpus it belongs to (a corpus key had no way to learn its own corpus id).
- A 401 for a wrong key now carries CORS headers, so a browser app can tell "wrong key" from a
  network error.
- `python -m callobuzz_rag.retrieval.reindex --rebuild --corpus <id> --apply` recreates a
  corpus's vector collection from Postgres — vectors and payloads — after a lost or corrupted
  Qdrant volume.
- `POST /api/v1/ingest/records`: import up to 1000 already-text records (FAQ entries, product
  listings, help articles, CMS/CRM exports) per call, with no file parsing. Records are keyed by
  your own `id`: re-importing replaces a changed record and skips an unchanged one, so re-syncing
  a whole catalogue only re-embeds what changed. Job status reports created / updated /
  unchanged counts. SDKs: `ingest_records()` (Python), `ingestRecords()` (JS).
- Retrieved chunks and citations carry `document_id` and `external_id`.
- Chunks carry their `section` (heading path) in `/retrieve`, citations and widget sources, and
  the LLM sees it in each citation header — "Adds offline checkout" is answerable as "which
  release?" only when the model also sees "Version 4.2.0".

### Changed — retrieval quality (measured on BEIR, see benchmarks/)
- Hybrid search is on by default in `Settings` too (it already was in `.env.example`).
- **Keyword search is now BM25**: saturating, length-normalized term weights, stopword removal
  and Snowball stemming, with the same analyzer at index and query time
  (`RAG_SPARSE_LANGUAGE`, `RAG_SPARSE_BM25_K1/_B`, `RAG_SPARSE_AVG_DOC_TOKENS`). The keyword leg
  alone went from 0.51 to 0.69 nDCG@10 on SciFact and 0.07 to 0.25 on FiQA. It also returns as
  many candidates as the dense leg instead of a fixed 20.
- **Chunks are indexed with their heading path** (a record's title) in front
  (`RAG_INDEX_HEADING_CONTEXT`); stored and returned text is unchanged. The reranker reads the
  same text.
- **Embedding models get their documented query/passage instructions** — for bge-*-en-v1.5,
  "Represent this sentence for searching relevant passages: " on queries
  (`RAG_EMBEDDING_QUERY_PREFIX` / `_PASSAGE_PREFIX` to override). HyDE's hypothetical answer is
  embedded as a passage.
- `python -m callobuzz_rag.retrieval.reindex` rebuilds keyword vectors (and, with `--dense`,
  re-embeds) in place for existing corpora; run it once after upgrading.

- **Hybrid search fuses by weighted, normalized scores** (`RAG_FUSION_STRATEGY=convex`,
  `RAG_HYBRID_DENSE_WEIGHT=0.75`) instead of equal-weight RRF. Tuned on BEIR dev/train, then
  measured on six test sets: mean nDCG@10 0.537, against 0.528 for dense alone and 0.505 for the
  RRF it replaces, which lost to dense on five of six. RRF stays available per corpus.
- Per-corpus `fusion_strategy`, `rrf_k`, `hybrid_dense_weight` and `mmr_lambda` now take effect;
  they were resolved and then ignored in favour of the global settings.
- `search_mode: "keyword"` — BM25 alone, no embedding call (exact lookups).
- `score_breakdown` carries each leg's raw `dense_score` and `sparse_score` next to its rank.
- `/query/retrieve` accepts queries up to 8000 characters (a whole passage: "find what is like
  this"); `/query` keeps its 2000-character cap for the prompt's sake.

- **Cross-encoder reranking is off unless a corpus turns it on** (`RAG_RERANKING_ENABLED`); the
  resolver used to force it on. Over hybrid retrieval, bge-reranker-v2-m3 raised nDCG@10 on
  the two BEIR Q&A sets (FiQA, TREC-COVID) and lowered it on the other four (mean 0.523 vs
  0.537), while adding ~0.5 s per query on a GPU and seconds on CPU. Enable it per corpus for
  Q&A-style content. `pipeline_order_enabled` stays off: with this reranker, keeping the fusion
  order scored higher than the cross-encoder's order on five of six datasets.

### Changed — performance
- **API key checks no longer block the server.** bcrypt verification ran synchronously on the
  event loop for every tenant/corpus-key request, serializing the API at ~5 requests/second.
  It now runs in a thread, and a verified key is remembered per process (by its SHA-256, bound
  to the stored hash, so rotation or deletion ends it at once). FiQA (57k documents), default
  settings: p50 latency 207 → 45 ms, single-client throughput 4.8 → 22 queries/second.
- MMR computes each candidate's similarity incrementally: 1048 ms → 40 ms at 100 candidates,
  identical results, and deterministic on ties.
- The in-process embedding model (`RAG_EMBEDDING_PROVIDER=local`) loads once per process
  instead of once per ingest task.
- `RAG_API_WORKERS` sets the number of API processes.
- The cross-encoder is preloaded only when reranking is on by default
  (`RAG_RERANK_WARMUP_ENABLED` unset follows `RAG_RERANKING_ENABLED`), so a default install no
  longer holds ~2.3 GB it never uses. CPU ingest through TEI keeps `RAG_TEI_CONCURRENCY`
  requests in flight.
- `RAG_DEBUG` no longer turns on SQL echo (which logged every statement with its parameters,
  document text included); that is `RAG_DB_ECHO`. `.env.example` now ships INFO logging.

### Fixed
- **Audio uploads were refused.** `POST /ingest` rejected every audio type although the
  pipeline transcribes audio. MP3, WAV, M4A, OGG, FLAC and WebM are now accepted when
  `RAG_TRANSCRIPTION_PROVIDER` is set, checked by container signature, and refused with a clear
  message when it is off.
- **0.1.0 listed "agentic mode, web search" as shipped.** The agent loop and web-search
  providers exist in code but no API route uses them yet; the README no longer claims them.
- **Embedding migrations dropped search filters.** Rebuilt payloads had `keywords=[]` and no
  category, user_id or custom metadata, so filters stopped matching after a migration (and after
  restoring an older document version). Document metadata is now stored in Postgres
  (`documents.doc_metadata`) and every rebuild builds its payload from it. Documents ingested
  before this release have their metadata only in Qdrant.
- **Deleting a corpus could leave it broken.** The vector collection was dropped before the
  database delete, which loaded every document, version and chunk through the ORM — slow enough
  on a large corpus to time out and roll back, leaving rows with no vectors. The database now
  goes first, in one SQL statement relying on ON DELETE CASCADE, and the collection after.
- Deleting a corpus now deletes its query log (the questions its users asked); `query_log` had
  no foreign key. `feedback → query_log` had lost its ON DELETE CASCADE in the initial
  migration.
- **PDF ingestion failed in the Docker image.** Docling fell back to RapidOCR's torch backend,
  which downloads weights into site-packages at parse time — as a non-root user, so every PDF
  failed with `Permission denied`. OCR now runs RapidOCR on onnxruntime with the models the
  package already ships (`RAG_OCR_ENGINE=rapidocr|tesseract|off`); scanned PDFs are read too.
- XLSX uploads were accepted by the API and then rejected by the parser; XLSX and CSV now
  parse. Legacy `.xls`, which the image cannot read, is refused at upload instead of failing
  after it.
- `/health` reported object storage as healthy when the configured bucket was missing (every
  upload then failed); it now checks the bucket, off the event loop.
- An API key matching no id prefix was bcrypt-checked against every corpus (and every tenant)
  — one request with a made-up key cost N bcrypt verifications. Keys are now looked up by
  their prefix only.
- The widget's per-minute limit used fixed windows, so a visitor could send twice the limit
  across a minute boundary; it is now a sliding window.
- `RAG_RERANK_TOP_N_INPUT` was never applied: the cross-encoder scored every fused candidate
  (up to ~200 on a wide hybrid query) instead of the top 50.
- A stale pooled connection to Qdrant failed the whole query with a 502; searches now retry
  transport errors (HTTP errors are not retried).
- LiteLLM embeddings ignored the query/passage distinction and embedded queries as passages.
- `/query/retrieve` returned only as many chunks as fit the LLM prompt budget
  (`RAG_CONTEXT_MAX_TOKENS`, 4096), so asking for `final_k: 50` could silently return 15. The
  budget now applies to answer generation only; `/retrieve` returns up to `final_k` chunks.
- `/query/retrieve` chunk text, answer citations and widget source snippets contained the
  prompt-injection wrapper (`<<<EXTERNAL_UNTRUSTED_CONTENT …>>>`); they now return the stored
  text, and only the LLM prompt is wrapped.
- A tenant key could read or confirm another tenant's ingest jobs, and list all jobs;
  job status, job listing and review confirmation are now tenant-scoped, and confirmation
  checks ownership before revealing or changing the job's state.

## [0.1.0] — 2026-09-28

First public release.

### Engine (already in place)
- Multi-tenant model: tenants → corpora, admin / tenant (`tk_`) / corpus (`ck_`) keys, per-corpus
  Qdrant collection, model, prompt and retrieval config, bring-your-own LLM key (Fernet, rotatable).
- Ingestion: PDF, Office, HTML, Markdown, audio (Whisper), web scraper; structure-aware chunking;
  near-duplicate review; versioned re-ingestion.

  web search.

  admin dashboard.
