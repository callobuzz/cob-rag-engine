# Security Policy

## Reporting a vulnerability

E-mail [callobuzz@gmail.com](mailto:callobuzz@gmail.com) with a subject that starts with
"SECURITY:". Please do not post a security problem in a public issue or anywhere else public.

Include:

- what you found and what an attacker could do with it;
- the steps to see it, or a short proof;
- the version (it is in `CHANGELOG.md` and in the dashboard) and how the product is set up
  (a normal install with `deploy/install.sh`, or something else);
- whether you want to be named when we publish the fix.

Please give us a reasonable time to release a fix before you tell others.

## What happens next

- **Acknowledgement:** we confirm that we received your report within 2 business days
  (Monday to Friday, India time).
- **Assessment:** within 5 business days we tell you whether we can reproduce it and how serious
  we think it is (critical, high, medium or low).
- **Fix targets, counted from the assessment:**

  | Severity | Fix released within |
  |---|---|
  | Critical | 14 days |
  | High | 30 days |
  | Medium | 90 days |
  | Low | the next release |

- **After the fix:** we tell you when it is released and, if you wish, credit you.
- **Advisories:** every fixed vulnerability is written up in a `### Security` section of that
  version's entry in `CHANGELOG.md`, with what was affected, what to do and the version that
  fixes it.

## Actively exploited vulnerabilities

Since 11 September 2026 the EU Cyber Resilience Act requires us to report a vulnerability that
is being actively exploited to ENISA, the EU's cybersecurity agency. We send an early warning
within 24 hours of learning of it, a notification within 72 hours, and a final report within
14 days after a fix is available.

We do not have the contact details of everyone who runs the product, so people learn about a
security fix in two places: the `### Security` section of the fixed version's entry in
`CHANGELOG.md`, and a notice on the public documentation. Install a security release as soon as
you can with `deploy/upgrade.sh`.

## Supported versions

The latest release is supported. A security fix is a new release; it is free for everyone.
`deploy/upgrade.sh` installs it, takes a backup first, and can roll back.

## Deployment hardening

The engine is multi-tenant and holds documents, embeddings and encrypted LLM
keys, so a few settings matter before any deployment is reachable by others.
They are all in `.env.example`, marked **⚠ PRODUCTION**:

- `RAG_ENV=prod` — disables the unauthenticated `/docs`, `/redoc` and
  `/openapi.json`, and refuses a wildcard `RAG_CORS_ORIGINS`.
- `RAG_BIND_ADDR=127.0.0.1` (the default) — keeps Postgres, Valkey and Qdrant
  off public interfaces. Docker's port publishing bypasses host firewalls
  such as UFW.
- Generate every secret (`make setup` does, and never prints them; `python
  scripts/generate_secrets.py` fills just the empty ones) and keep a backed-up
  `RAG_ENCRYPTION_KEY`. Without one, the app generates a throwaway key
  on each boot and previously encrypted LLM keys become unreadable.
- Keep `RAG_ADMIN_API_KEY` server-side; give applications tenant (`tk_`) or
  corpus (`ck_`) keys instead.
- `RAG_SESSION_SECRET` (generated by `make setup`) signs dashboard sign-ins; keep
  it secret and rotate it by putting a new value first in the comma-separated
  list. `RAG_CORS_ORIGINS` must list the dashboard's origin, and
  `RAG_DASHBOARD_URL` must point at it.

## Accounts: what protects them

People sign in to the dashboard; applications keep using keys. The properties
below are covered by unit and integration tests and by the account attacks in
`benchmarks/ops.py` (forged and replayed tokens, a member on owner-only routes,
invitation abuse, a removed member, a suspended tenant's every credential,
sign-up and forgot-password enumeration, the login lockout).

- **Passwords** are hashed with argon2id (RFC 9106 low-memory profile), 10 to
  128 characters, not among the 10,000 most common, not containing the e-mail's
  name part. A wrong e-mail and a wrong password get the same answer, and an
  unknown address costs the same hashing time.
- **Tokens.** Access tokens are HS256 JWTs valid 15 minutes, bound to a server
  session that every request re-reads (so revocation, removal, role changes and
  suspension apply on the next request). Refresh tokens rotate on every use and
  are stored hashed; presenting the one just replaced revokes the whole session.
  Sessions slide for 30 days and end after 90 at most. A password change or
  reset ends the other sessions.
- **Codes and links.** Sign-up, reset and set-password codes are 6 digits,
  HMAC-hashed, valid 10 minutes (24 hours for the super admin's first one), 5
  tries, and a newer one voids the older. Invitation tokens are 256-bit, single
  use, 7 days, stored hashed. Links carry codes and tokens in the URL
  `#fragment`, which browsers never send to a server; nothing secret goes in a
  URL the engine receives, in a log line or in the audit log.
- **Limits fail closed.** Sign-in, sign-up, codes and invitations are
  rate-limited in Valkey per IP and per address, with a lockout that starts at
  the fifth wrong password (1 minute, doubling to 15). If Valkey is down these
  routes answer 503 rather than run unlimited.
- **No enumeration.** Sign-up, resend and forgot-password answer every address
  the same way.
- **Roles.** A workspace member cannot create or delete knowledge bases,
  delete, replace or restore documents, manage keys, set the model key or
  manage the team (403 `owner_required`); only the operator sees the audit log
  and webhooks.
- **Suspension** stops a tenant's keys, widgets and sign-ins at once, and needs
  the tenant's exact name, as does deletion.
- **Audit log.** Operator and account actions are recorded (`GET
  /api/v1/admin/audit`, operator only) and kept indefinitely.

Report a weakness in any of these the same way as any other vulnerability
(above).
