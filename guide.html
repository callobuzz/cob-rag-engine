01What you’ll have running#

cob-rag-engine is a self-hosted knowledge engine. Each business you serve (a customer, called a tenant in the API) gets private knowledge bases: its documents go in, and cited answers come out through a website chat widget, your own app, or an AI agent. You run one Docker Compose stack: the engine API, a background worker, a mailer, a scheduler, a web scraper, the dashboard, and the datastores (PostgreSQL, Redis, Qdrant, MinIO and the embedding container). This guide takes you from a fresh clone to a first customer with a working widget, then covers day-to-day running and what to do when something breaks.

ServiceAddressWhat it is
Dashboardhttp://127.0.0.1:8090Where you and your customers sign in. Port variable RAG_DASHBOARD_HOST_PORT.
Engine APIhttp://127.0.0.1:8000The REST API. Interactive docs at /docs while RAG_ENV=dev. Port variable RAG_APP_HOST_PORT.
Web scraperhttp://127.0.0.1:8001Crawls a customer’s website for the dashboard’s Crawler page. Port variable RAG_SCRAPER_HOST_PORT.
MinIO consolehttp://127.0.0.1:9003Browse uploaded files. The S3 API is on 9002. Bundled storage (profile local-storage, on by default).
Embeddings (TEI)127.0.0.1:8081The embedding model container (profile tei, on by default).
Langfusehttp://127.0.0.1:3002Optional: traces of every question (profile observability).
Whisper127.0.0.1:9010Optional: audio transcription (profile transcription). Port variable RAG_WHISPER_HOST_PORT.
Datastores5433 6380 6333/6334PostgreSQL, Redis and Qdrant. You never need to open these.
Good to know
Every port is published on 127.0.0.1 only (RAG_BIND_ADDR), so only your own machine can reach the stack. The three web ports are configurable through RAG_APP_HOST_PORT, RAG_SCRAPER_HOST_PORT and RAG_DASHBOARD_HOST_PORT; step 4 shows how the wizard changes them for you. The other ports are fixed in docker-compose.yml.

02Before you start#

2.1Software#

  • Docker with Compose v2: Docker Desktop on Windows or macOS, Docker Engine on Linux. You need the docker compose command (two words), not the old docker-compose.
  • Python 3.10 or newer, only for the setup wizard. The wizard uses the standard library, so there is nothing to pip install and no virtualenv to create.
  • git, to clone the repository.
  • make is optional. make setup is only a shortcut for python scripts/setup.py.

Check what you have:

Terminal
docker --version
docker compose version
python --version
git --version
Tip
If python is not found, install Python 3.10 or newer (on Windows tick “Add python.exe to PATH” in the installer). On macOS and Linux the command is often python3; make setup runs python, so use the python3 scripts/setup.py form there.

2.2Your machine#

  • Memory: 4 GB of RAM or more for Docker. The default stack measured 2.1 GB on CPU with 270,000 chunks indexed. Turning on the local re-ranker on CPU adds about 2.3 GB.
  • Disk: the repository does not state a figure. The first start builds three images and downloads several more plus an embedding model, so keep several GB free. Ten GB is a comfortable margin; that number is a rule of thumb, not something we measured.
  • An NVIDIA GPU is optional. It only makes the local models faster (the embedding model and a local re-ranker), not better. Hosted APIs and LLM re-ranking run at the provider either way. To see whether Docker can use your GPU, run this (it is the same check the wizard suggests; it downloads a small image the first time):
Terminal
docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi

If it prints a table with your GPU, Docker can use it. If it fails, answer “no” to the GPU question later; everything works on the CPU.

2.3An AI model key#

Answers are written by a language model, so you need one provider key: OpenRouter (one key, hundreds of models), OpenAI, Anthropic (Claude), Google Gemini, or a local Ollama with no key at all. You can skip this during setup: uploading and searching work without a key, and only answering needs one. The key is stored in your local .env file and nowhere else.

04Configure with the setup wizard#

The wizard asks a few questions, generates every secret, and writes one file: .env in the repository root. Keys you type are hidden and never printed back.

4.1Run it#

Git Bash
python scripts/setup.py
# or, if make is installed: make setup
PowerShell
python scripts/setup.py
Terminal
python3 scripts/setup.py
# or: make setup

It opens with “How much do you want to set up?” Press Enter to accept the answer in [brackets] at any prompt.

4.2Quick or full#

  • Quick (the default, recommended): the GPU question once, then your e-mail, the AI model, how to send e-mail, and the re-ranker. Start here.
  • Full: also asks about the environment (development or production), where embeddings run, where uploaded files are stored, the web addresses and host ports, the network bind address, and the optional services (audio transcription, Langfuse). Choose it with --full; --quick forces quick mode.

4.3What each answer means#

GPU
“Do you have an NVIDIA GPU that Docker can use?” It is asked once, first, and yes / no / not sure (not sure is treated as no and prints the check from step 2). The answer decides three things: whether the start command includes the GPU overlay, whether the bundled embedding container (TEI) uses its CUDA image, and where a local re-ranker runs. --gpu yes or --gpu no answers it up front.
Super-admin e-mail
The account you sign in to the dashboard with, for example admin@yourcompany.in. It gets a link to set its password. Press Enter to skip; you then sign in with the admin API key instead (step 6).
AI model
Pick a provider and a model; the wizard suggests one per provider (OpenRouter openai/gpt-oss-20b, OpenAI gpt-4o-mini, Anthropic claude-haiku-4-5, Gemini gemini-2.5-flash, Ollama llama3.1). Then paste the key, which is hidden. For Ollama it asks for the address, http://host.docker.internal:11434 by default, because from inside Docker your machine is host.docker.internal. Choose “Skip for now” to add the key later as RAG_LLM_API_KEY in .env.
E-mail sending
E-mail carries sign-up codes, password resets and invitations. Skip is fine on your own machine: in development the codes and links go to the logs (step 7 shows where). Gmail or Google Workspace needs an app password (2-step verification on, then create one). Another SMTP server asks for host (for example smtp.zoho.in), port, connection security, login and a sender such as Shree Labs <no-reply@shree-labs.in>.
Re-ranker
A second pass that re-reads the top search results and reorders them. Off is the safe start. In the project’s benchmarks the local model helped on question-and-answer data (the chatbot case) and hurt on other kinds of search; re-ranking through your LLM has not been measured yet. The options follow your GPU answer. With a GPU: off, local on the GPU (about 0.4 s a question), or through your LLM. Without one: off, through your LLM (small cost per question), or local on the CPU (free but about 10 s a question and 2.3 GB of RAM). You can change it per knowledge base later in the dashboard (Knowledge base, then Retrieval).
Embeddings
Quick mode does not ask. It uses the bundled TEI container with the model BAAI/bge-base-en-v1.5, on your GPU if you said yes and on the CPU otherwise. Full mode lets you choose: TEI on CPU, TEI on GPU (offered only if you said yes), inside the engine (BGE-M3), or a hosted API (OpenAI, Cohere, Voyage, Mistral, Gemini or Jina). Changing the embedding model for a knowledge base that already has documents needs a re-embed.
Warning
On Docker Desktop for Windows, TEI’s CUDA image cannot see the GPU (the README says so). If you are on Windows with a GPU, quick mode already handles this: it runs the engine’s own embedding model on the GPU instead of TEI.

4.4Without the questions#

For scripts, CI or a repeat install, every question can be answered on the command line. --yes accepts every default and asks nothing, --set KEY=VALUE sets any value (repeat it as often as you like), and --dry-run shows what would change, with secrets masked, and writes nothing.

Terminal
python scripts/setup.py --quick --yes --set "RAG_SUPERADMIN_EMAIL=admin@yourcompany.in"
python scripts/setup.py --quick --yes --gpu yes
python scripts/setup.py --dry-run

--yes cannot ask for your LLM key. Add RAG_LLM_API_KEY to .env afterwards, or run the wizard once without --yes. On macOS and Linux write python3 for python.

4.5Running it again later#

Re-running is safe. The wizard copies your old file to .env.backup-<timestamp> first, keeps every value you already have and every key it does not know, and only changes what you answer (it asks “Already set. Keep current?” for things like your key). At the end it prints a summary, a “Worth a look” list of things to double-check, and the exact start command for your choices.

Warning
Keep a safe copy of RAG_ENCRYPTION_KEY from .env. Without it, the LLM keys stored by your customers are unreadable. See backing it up. Never commit .env or paste it into a chat.

05Start the stack#

5.1Run the command the wizard printed#

The wizard ends with the exact command for your choices. For most people it is the first one below; with an NVIDIA GPU it includes the GPU overlay. make up and make up-gpu run the same two commands. Optional services (transcription, Langfuse) come from COMPOSE_PROFILES in .env, which the wizard sets.

Terminal
docker compose up -d --build
With an NVIDIA GPU
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build

5.2The first start takes a while#

The first run builds the engine, scraper and dashboard images, pulls the datastore images, and downloads the embedding model. The compose file gives the embedding container a 120 second grace period before it even checks its health, then 30 checks ten seconds apart, because the model download is the slow part. Models are kept in a Docker volume, so later starts are quick. You can watch it with docker compose logs -f tei.

5.3Wait until it is healthy#

Terminal
docker compose ps

Run it again every minute or so until the app service says healthy. When it does, the engine’s health URL answers in your browser. The engine runs its database migrations by itself as it starts, so there is nothing to migrate by hand. If something stays unhealthy or keeps restarting, jump to reading the logs.

06First login#

6.1Get your set-password link#

With a super-admin e-mail set, the engine creates that account on its first start. If you configured SMTP, a set-password link is e-mailed to you. If you skipped e-mail, the engine prints a one-time link to the app’s log instead:

Git Bash
docker compose logs app | grep -A4 "ONE-TIME SET-PASSWORD"
PowerShell
docker compose logs app | Select-String -Context 0,4 "ONE-TIME SET-PASSWORD"
Terminal
docker compose logs app | grep -A4 "ONE-TIME SET-PASSWORD"

The output shows the account, a link and a code. Open the link, which is valid for 24 hours, and choose a password: 10 to 128 characters, not one of the 10,000 most common, and not containing the name part of your e-mail. Until you set it, every start of the app issues a fresh code and voids the old one, so if you see several, use the last.

6.2Open the dashboard#

Go to http://127.0.0.1:8090 and sign in with your e-mail and the new password.

Tip
Type 127.0.0.1, not localhost. On Windows with Docker Desktop, localhost resolves to the IPv6 address ::1 first, and the connection resets in a way that looks exactly like the service being down.

6.3No e-mail set? Use the admin key#

If you skipped the super-admin e-mail, click Use an API key instead on the sign-in page and paste the admin key, which is RAG_ADMIN_API_KEY in .env. This prints only that one line:

Git Bash
grep RAG_ADMIN_API_KEY .env
PowerShell
Select-String RAG_ADMIN_API_KEY .env
Terminal
grep RAG_ADMIN_API_KEY .env
Warning
The admin key can do everything on the engine. Treat it like a root password and do not share your terminal output.

07Try the whole flow#

This walks one customer from sign-up to a working chat bubble. The example is Shree Labs, a pathology lab in Pune. You play two roles: the operator (you, signed in as the super admin) and the customer’s owner. Use a private browser window for the customer so the two sessions do not collide.

7.1Choose how customers join#

The Customers page shows the current sign-up mode; you change it under Sign-up & branding. There are three:

  • Approval required (the default): a new workspace waits as pending until you activate it.
  • Open: the workspace is active the moment the customer verifies their e-mail.
  • Closed: sign-up is refused with your “contact us” text.

You can also skip sign-up: Customers, then Add customer creates an active workspace by hand, and you then invite its owner. That path works even with no e-mail set up, because an invitation sent by the operator shows the accept link on screen.

7.2Create a customer#

  1. In the private window open http://127.0.0.1:8090/signup. Enter the business name (Shree Labs), your name, an e-mail that is not the super admin’s (for example owner@shree-labs.in) and a password.
  2. The dashboard asks for a 6-digit code. It works for 10 minutes and 5 tries. With SMTP it arrives by e-mail. Without SMTP it is in the mailer’s log:
Git Bash
docker compose logs mailer | grep -A12 "DEV EMAIL"
PowerShell
docker compose logs mailer | Select-String -Context 0,12 "DEV EMAIL"
Terminal
docker compose logs mailer | grep -A12 "DEV EMAIL"

Each message is printed in full after the words DEV EMAIL; take the code from the newest one. Enter it, and the workspace is created with you as its owner.

7.3Activate it#

In approval mode the customer now sees “We’ll activate your workspace soon”. As operator, open Customers, the Pending tab, and choose Activate. Pick a plan and, if you like, add a private note such as “Paid ₹3,000 via UPI on 29 Sep”. The owner gets a “You’re in” e-mail (in the mailer log without SMTP). Activation is not billing: collect payment however you like, then activate.

7.4Create a knowledge base#

As the customer’s owner open Knowledge bases, then New knowledge base, and name it Shree Labs FAQ. A knowledge base has its own documents, model settings, search index and API key. The key is shown once at creation.

7.5Upload something#

Open Add content and drag in a file, for example the lab’s test menu with prices in ₹ and fasting instructions. You watch each file go through queued, parsing, chunking, embedding and done. PDF, Word, PowerPoint, Excel, CSV, HTML, Markdown, plain text, PNG and JPEG are accepted, and audio (mp3, wav, m4a, ogg) when the transcription service is on. You can also crawl a website from Crawler (you review the pages before they go in) or import records from JSON or CSV. See upload size limits before you try a large file.

7.6Ask in the playground#

Open Playground, pick the knowledge base, and ask something the document answers, such as “Do I need to fast before a lipid profile?” You get an answer with the passages it used. This step needs the LLM key from step 4; without one, answering fails until you add RAG_LLM_API_KEY. An owner can also give one knowledge base its own model and key.

7.7Add the website widget#

  1. Open Website widget and choose New widget key. Name it, and list the sites allowed to use it, one address each (for example https://shree-labs.in; plain http:// is accepted only for localhost and 127.0.0.1). Set the messages per minute for each visitor and per day, and the title, greeting, colour and corner.
  2. Copy the embed snippet and paste it into the website before the closing </body> tag:
HTML
<script src="http://127.0.0.1:8000/widget.js" data-key="pk_..." async></script>

Optional attributes are data-open="true" (open the chat on load), data-position="left" and data-color="#0f766e". The pk_ key is meant to be visible in page source: it can only chat with its one knowledge base, only from the sites you listed, and only within the limits you set. The chat panel always shows a small “cob-rag-engine by Callobuzz” link; no setting hides it.

To see it before touching a real site, choose Preview and style on the key. That shows the real widget on a sample website, at phone or desktop width, served from the dashboard at /widget-demo.html. For a live site, set RAG_PUBLIC_URL to your engine’s public HTTPS address so the snippet points there.

7.8Invite a teammate#

In the customer’s dashboard open Team and choose Invite teammate. They can be an Owner or a Member. The invitation link is valid for 7 days and works once. Members can use the playground, view everything, upload content and edit prompts and retrieval settings. Owners can also create or delete knowledge bases, manage API and widget keys, set the model key, and manage the team.

7.9Plans and limits#

Open Plans as operator. A fresh install has one plan, Standard, with no limits. A plan can cap four things, each optional: knowledge bases, questions per month, active documents and website widget keys. Move a customer between plans from Customers, then Change plan. Customers see their own usage against the caps under Plan & usage, and you see metered usage per customer under Usage. Payments are not built in: the usage meter is what you bill from.

08Connect an AI agent (MCP)#

cob-rag-mcp is a companion MCP server and command-line tool that plugs a knowledge base into Claude, Cursor, VS Code, n8n or any MCP client. It is only a client: it talks to the engine you just started, and nothing is sent anywhere else. You need Node.js 22 or newer.

8.1What it needs#

The engine address (http://127.0.0.1:8000 here) and a key. Use the knowledge base’s own key (it starts with ck_), which lets the agent see that one knowledge base and nothing else. The server asks the engine who the key is and offers only the tools that key may use. Destructive tools stay hidden unless you set COB_RAG_ALLOW_DESTRUCTIVE=true.

8.2Claude Code#

Git Bash
claude mcp add cob-rag \
  -e COB_RAG_URL=http://127.0.0.1:8000 \
  -e COB_RAG_API_KEY=ck_your_corpus_key \
  -- npx -y cob-rag-mcp start
PowerShell
claude mcp add cob-rag -e COB_RAG_URL=http://127.0.0.1:8000 -e COB_RAG_API_KEY=ck_your_corpus_key -- npx -y cob-rag-mcp start
Terminal
claude mcp add cob-rag \
  -e COB_RAG_URL=http://127.0.0.1:8000 \
  -e COB_RAG_API_KEY=ck_your_corpus_key \
  -- npx -y cob-rag-mcp start

8.3Claude Desktop and everything else#

For Claude Desktop, add this to claude_desktop_config.json (macOS: ~/Library/Application Support/Claude/, Windows: %APPDATA%\Claude\) and restart it:

claude_desktop_config.json
{
  "mcpServers": {
    "cob-rag": {
      "command": "npx",
      "args": ["-y", "cob-rag-mcp", "start"],
      "env": {
        "COB_RAG_URL": "http://127.0.0.1:8000",
        "COB_RAG_API_KEY": "ck_your_corpus_key"
      }
    }
  }
}

Cursor, VS Code, n8n, the streamable HTTP mode and the cob-rag-engine command-line tool are covered in the cob-rag-mcp README and on its website; the package is on npm. The dashboard’s Agents (MCP) page links there too.

09Day-to-day#

Run these from the repository folder. Each has a make shortcut where one exists.

9.1See what is running and read logs#

Terminal
docker compose ps
docker compose logs -f --tail=100 app
# every service at once:
docker compose logs -f --tail=100

The services are app, worker, mailer, celery-beat, scraper, dashboard, postgres, redis, qdrant, minio and tei. make ps and make logs are the shortcuts.

9.2Restart one service#

Terminal
docker compose restart app

A restart does not re-read .env. After you edit .env, run the start command again (docker compose up -d); Compose recreates only the services whose settings changed. For the dashboard alone: docker compose up -d dashboard.

9.3Stop and start again without losing data#

Terminal
docker compose down

This stops and removes the containers but keeps every named volume: the database, vectors, uploaded files and model cache. make down does the same. Start again with the same command you used the first time (docker compose up -d; add --build only after an update). The containers also come back on their own when Docker starts, because they are set to restart unless stopped.

9.4Update to a new version#

  1. Read CHANGELOG.md for the release you are moving to. It lists upgrade notes.
  2. Fetch the new code: git pull.
  3. Re-run the wizard so new settings are added and your values are kept (see step 4.5).
  4. Rebuild and restart:
Terminal
git pull
python scripts/setup.py
docker compose up -d --build

Database migrations run automatically: the app’s entrypoint runs alembic upgrade head before it starts serving, and stops with “ERROR: Alembic migration failed!” in docker compose logs app if one fails. On macOS and Linux write python3 for python, and add the GPU overlay to the last command if you use one.

Warning
Some updates change what Docker creates. For example, the compose project was renamed to cob-rag, and an install from before that rename starts with new, empty volumes. Always read the changelog first.

10Tear down and reset#

10.1down versus down -v#

docker compose down stops the stack and keeps your data. docker compose down -v also deletes the volumes.

This deletes data
docker compose down -v permanently deletes the database, vector store, uploaded files, Redis data and model cache: every customer, knowledge base, document and account on this install. There is no undo. Use it only when you want to start from nothing. (make clean runs the same down -v and also removes Python cache folders.)
Terminal
docker compose down -v

10.2Remove the images too#

The images take disk space. This stops the stack, deletes the volumes and removes the images Compose used (Docker skips any image another project still uses):

Terminal
docker compose down -v --rmi all

10.3Start completely fresh#

  1. Delete the data: docker compose down -v.
  2. Move the old settings aside. The wizard keeps the values it finds, so to get brand-new secrets the file has to be gone:
Git Bash
mv .env .env.old
PowerShell
Rename-Item .env .env.old
Terminal
mv .env .env.old

Then run the wizard again (step 4) and start the stack (step 5).

Warning
Delete the volumes whenever you replace .env. PostgreSQL only reads its password when its volume is first created, so new secrets with the old volume leave the app unable to sign in to the database. To reset the data but keep your settings, leave .env in place.

11Troubleshooting#

Each item reads symptom, why it happens, fix. Start with docker compose ps and docker compose logs <service>; they answer most questions.

11.1Port already in use#

Symptom
docker compose up fails with a message like “port is already allocated” or “address already in use”.
Why
Another program on your machine already uses one of the ports (8000, 8001, 8090, or a datastore port such as 5433 or 6380).
Fix
Find it, then free it or move the stack. To see who holds a port (8000 here):
Git Bash
netstat -ano | findstr :8000
PowerShell
netstat -ano | findstr :8000
Terminal
lsof -i :8000
To move the three web ports, re-run the wizard with --full (it asks for the host ports and updates the matching addresses and allowed origins), or pass one directly:
Terminal
python scripts/setup.py --quick --yes --set "RAG_APP_HOST_PORT=8100"
Then run the start command again. The datastore, MinIO, TEI and Qdrant ports are fixed in docker-compose.yml; stop whatever uses them instead.

11.2Docker Desktop is not running#

Symptom
Every docker command fails with “Cannot connect to the Docker daemon” or, on Windows, a pipe error such as “The system cannot find the file specified”.
Why
The Docker engine is not started. Docker Desktop has to be open (or the Docker service running on Linux) before any compose command works.
Fix
Start Docker Desktop and wait until it says the engine is running, then check with docker info. On Linux start the service (sudo systemctl start docker). Then run the start command again.

11.3Containers are unhealthy or restarting#

Symptom
docker compose ps shows unhealthy, Restarting or Exited for a service.
Why
Something the service needs is missing or wrong. The last lines of its log almost always say what.
Fix
Read the log of that service, newest lines last:
Terminal
docker compose logs --tail=100 app
Replace app with the service name. Causes the wizard itself warns about: RAG_SMTP_HOST set but RAG_SMTP_FROM empty (the engine will not start); RAG_ENV=prod with RAG_EMAIL_PROVIDER=log (refused); RAG_EMBEDDING_PROVIDER=tei without tei in COMPOSE_PROFILES (ingestion fails). A line such as “set RAG_DB_PASSWORD in .env” means a required secret is empty: re-run the wizard. A failed migration shows “ERROR: Alembic migration failed!” in the app log. After fixing .env run docker compose up -d.

11.4The first start is very slow#

Symptom
docker compose ps shows tei as starting for minutes, and the app does not become healthy.
Why
The embedding container downloads its model (BAAI/bge-base-en-v1.5) on first start, and the images are being built. This is normal.
Fix
Wait, and watch docker compose logs -f tei. The compose file allows TEI 120 seconds before the first health check and then 30 checks ten seconds apart. The download is cached in a Docker volume, so the next start is fast. If you chose a local re-ranker or in-engine embeddings, those models download too.

11.5The GPU is not used#

Symptom
Embeddings or the re-ranker run slowly, the TEI log does not say it is starting the model on Cuda, or Compose refuses to start a service with “could not select device driver nvidia”.
Why
Compose refuses to start a service that reserves a GPU the host does not have, which is why the GPU overlay is never the default. The TEI container also needs the CUDA image, not the CPU one. On Docker Desktop for Windows, TEI’s CUDA image cannot see the GPU.
Fix
Run the GPU check from step 2. If it fails, answer “no” (python scripts/setup.py --gpu no) and use the plain start command. If it works, answer yes and use the GPU start command. On Windows, quick mode picks the engine’s own embeddings for you, which use your GPU without TEI. For TEI on Linux with a specific card you can set RAG_TEI_IMAGE to the tag for its generation: turing-1.9, 86-1.9 (Ampere), 89-1.9 (Ada), hopper-1.9, 120-1.9 (Blackwell) or the portable cuda-1.9, all under ghcr.io/huggingface/text-embeddings-inference. The local re-ranker alone needs about 2.3 GB of GPU memory.

11.6localhost does not work on Windows#

Symptom
http://localhost:8090 resets or never loads, but the containers are healthy.
Why
On Windows with Docker Desktop, localhost resolves to the IPv6 address ::1 first, and Docker Desktop resets that connection. It looks exactly like the service being down.
Fix
Use http://127.0.0.1:8090 (and 127.0.0.1 in every address you put in .env).

11.7The dashboard cannot reach the engine#

Symptom
The dashboard loads but shows a network or connection error, or every call fails in the browser.
Why
Your browser calls the engine and the scraper directly. Two settings must match the address you actually use: RAG_DASHBOARD_ENGINE_URL and RAG_DASHBOARD_SCRAPER_URL (where the browser reaches them), and RAG_CORS_ORIGINS (which must list the dashboard’s own origin; the scraper has SCRAPER_CORS_ORIGINS). They break when you change a port, open the dashboard from another address, or put the stack behind a domain. The dashboard’s Content-Security-Policy only allows calls to the two configured addresses.
Fix
First check the engine itself: http://127.0.0.1:8000/api/v1/health should answer. Then run python scripts/setup.py --full and set the “Web addresses” (it merges the dashboard’s origin into both CORS lists), and recreate the services with docker compose up -d. For a live deployment use your public https addresses.

11.8There is no set-password link#

Symptom
You search the logs and find no “ONE-TIME SET-PASSWORD” block, or no e-mail arrived.
Why
The link is only created when RAG_SUPERADMIN_EMAIL is set (otherwise the log says “No RAG_SUPERADMIN_EMAIL; skipping”), and the account needs RAG_SESSION_SECRET, which the wizard generates. With SMTP the link is e-mailed, not printed. Old log lines may also have rotated away.
Fix
Re-run the wizard and enter the e-mail (or --set "RAG_SUPERADMIN_EMAIL=admin@yourcompany.in"), then restart the app with docker compose up -d app. To issue a new link and print it on screen right now:
Terminal
docker compose exec app python -m callobuzz_rag.accounts.bootstrap --resend --print-link
If your password is already set, --resend issues a fresh code anyway.

11.9Sign-up codes do not arrive#

Symptom
A customer signs up but no 6-digit code shows up in their inbox.
Why
If you skipped SMTP in the wizard, nothing is sent: in development (RAG_ENV=dev) every message is written to the mailer’s log instead. With SMTP, the mail server may be refusing the message. In production (RAG_ENV=prod) with no SMTP, e-mail is disabled and sign-up is unavailable.
Fix
Read the code from the log:
Git Bash
docker compose logs mailer | grep -A12 "DEV EMAIL"
PowerShell
docker compose logs mailer | Select-String -Context 0,12 "DEV EMAIL"
Terminal
docker compose logs mailer | grep -A12 "DEV EMAIL"
With SMTP, check the same log for errors, and use Email (SMTP) in the operator dashboard to check the configuration and send yourself a test. Temporary failures are retried after 15, 30, 60, 120 and 240 seconds, and a message whose code would already have expired is dropped (codes last 10 minutes), so ask for a new code.

11.10“Too many attempts” or a sign-in lockout#

Symptom
The dashboard says “Too many attempts. Try again in …” or “Too many tries. Login is paused for …”.
Why
The engine rate-limits the account routes. Sign-in allows 10 tries per e-mail per 15 minutes and 30 per address per 5 minutes. From the fifth wrong password in 15 minutes the e-mail is locked for 1 minute, doubling each further failure up to 15 minutes, and the lock refuses even the right password. Sign-up allows 5 per hour from one address and 3 per hour for one e-mail. The limits live in Redis, and if Redis is down the engine refuses rather than running unlimited (“Sign-in is briefly unavailable”).
Fix
Wait for the time the message gives. A correct sign-in, or finishing a password reset, clears the failure count and the lock. If you see “briefly unavailable”, check docker compose ps redis.

11.11“Workspace not active”#

Symptom
A customer sees “We’ll activate your workspace soon” or “<name> is paused”, or their key gets a 403 workspace_not_active.
Why
The workspace is pending (approval mode, not activated yet) or suspended. Their people can still sign in and see the status page; keys, widgets and agents are refused, and widget visitors see “This assistant is not available right now.”
Fix
As operator, open Customers. Choose Activate on the Pending tab, or Reactivate on the Suspended tab. It takes effect on the next request and nothing was deleted.

11.12A plan limit message#

Symptom
“Monthly question limit reached (412 of 1,000). It resets on …”, or “Your plan allows N knowledge bases / documents / website widget keys.”
Why
The customer’s plan has a cap and they reached it. The month is the calendar month in UTC. Searches that only retrieve passages are not counted, and cached answers do not count. The admin key and super admin are never capped.
Fix
Move the customer to a bigger plan (Customers, then Change plan) or edit the plan under Plans. Lowering a limit never deletes anything; it only blocks new additions. At the question cap, widget visitors see a polite “not available” message and nothing about the plan.

11.13An upload is refused as too large#

Symptom
The upload fails with “File too large (max 50MB)” or “File too large (~N estimated tokens). Max ~500K tokens.”
Why
There are two limits in src/callobuzz_rag/api/routes/ingest.py. A file over 50 MB is refused. But the engine also estimates the size as bytes divided by 4 and refuses anything over 500,000 estimated tokens, which is about 2 MB of file. So the limit you will actually hit is about 2 MB per file, not 50 MB.
Fix
Split the document into smaller files, or export its text and import it as records (Add content, then Records import, or POST /api/v1/ingest/records), which takes up to 1,000 records per request and up to 200,000 characters of text in each. The dashboard shows the effective limit when you add content.

11.14Answers are slow#

Symptom
The playground or widget takes many seconds to answer.
Why
Most of the time is the language model: a large model, a slow provider, or Ollama running on a CPU. The second common cause is the local re-ranker on a CPU, which the wizard measured at about 10 s a question.
Fix
Choose a faster model (RAG_LLM_MODEL, or per knowledge base in the dashboard). Turn the re-ranker off, or use it on a GPU or through your LLM: re-run the wizard and answer the re-ranker question, or change it under the knowledge base’s Retrieval settings.

11.15I forgot the admin password#

Symptom
You cannot sign in to the dashboard as the super admin.
Why
Passwords are stored as hashes, so nobody can read them back, but there are two ways in.
Fix
Use Forgot password? on the sign-in page. It sends a reset code to your e-mail (without SMTP, find it in the mailer log as in the sign-up item above). Or sign in with the admin key through Use an API key instead (RAG_ADMIN_API_KEY in .env). Or issue a new set-password link with the bootstrap --resend --print-link command from the “no set-password link” item. Finishing a reset also clears any sign-in lockout.

11.16Where is the admin API key?#

Symptom
You need the admin key for the API, the MCP server, or the dashboard’s key sign-in, and you do not remember it.
Why
The wizard generated it and, like every secret, never printed it.
Fix
It is RAG_ADMIN_API_KEY in the .env file in the repository root. Print just that line with the command in step 6.3. Send it in an X-API-Key header. Keep it private: it can do everything on the engine.

11.17Back up RAG_ENCRYPTION_KEY#

Symptom
You are moving to a new machine, rebuilding, or worried about losing .env.
Why
RAG_ENCRYPTION_KEY encrypts the LLM keys your customers store in their knowledge bases. Without it those stored keys cannot be read, and every customer would have to paste theirs again. It is generated once and never printed.
Fix
Copy it into a password manager now, apart from the repository. The wizard’s .env.backup-* files and your .env hold all your secrets, so store them as carefully as the key. The engine can rotate the key, and python -m callobuzz_rag.core.reencrypt rewrites stored tokens under the new primary key; see the README’s Operations section.
